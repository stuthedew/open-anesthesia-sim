# Write plainly

**Resident, with no `paths:`.** It applies whenever a session writes prose. A
path scope would miss item briefs, commit messages, pull request bodies and
replies, because no read comes before them. The project owner asked for this
rule on 2026-10-17, and `PL-8ZTQ` has the measurement and the sources behind
each point.

Write all prose that a person will read in plain English: docstrings, comments,
error messages, documents, rules, item briefs, commit messages, pull request
titles and bodies, replies, and every question or review request sent to the
project owner, including each field of the line `bin/docket arm` prints. In
those, say what changes for the owner or a learner, and never name a test,
check or tool by its internal name (project owner, 2026-11-02, `PL-BGN1`).
Write for the readers that the table below names for that kind of text. They
should understand each sentence the first time they read it (project owner,
2026-11-02, ratified, `PL-H76S`).

The two `README.md` rows are the readers that `README.md` § "What it is for"
names. `docs/releases/` has no row, because `bin/docket release` writes each
note from item titles, and an edit there would make a note disagree with its
item. `tools/new_prose.py` reads this table. It prints a changed file's passages
for the copy editor only when a row names that file, and it gives each passage
that row's readers. A new row therefore brings the files it names into the
review with no other change.

**Write what the reader needs to act on, and stop.** Find the reader and what
they will do with the text in the table above. Put what they see first, then
what it means for them, then why. Move each reason, derivation, test name and
piece of history that they do not act on to where its own reader looks, or cut
it. Decision history goes in the item. In `docs/MODEL.md`, the rest goes in a
note for developers at the end of the section it came from, a paragraph that
opens with "**For developers.**" That note may name the tests for the paragraphs
directly above it (`PL-W8FL`). That detail stays in `docs/MODEL.md`, because the
document must specify the numerical method (`PL-TZ7R`). State a model limitation
only where it could change what a clinician concludes from a displayed value
(`PL-BS6N`).

**Give a chosen value its reason from a record.** Where a docstring or a
comment gives a chosen value, such as a tolerance or a limit, say what the
value does, why it is this number, and what changing it would do. In
`docs/MODEL.md`, say it in the note for developers. Take each answer from the
code or test that uses the value, or from a cited record. When the reason is
not at hand, trace the value's history first, with `git log -S` and the items.
Search for the value as the code writes it. The step-size test's 0.5% tolerance,
removed in `PL-VXM0`, was `5e-3` in `tests/reference/test_sevo_patient.py`, and
`git log -S 5e-3` finds the commit that first set it. When the trace finds no
reason, file an item for the missing record, and say in the text what the trace
found. Never state a reason that no record holds.

1. **Write whole sentences.** Keep the small words that show how a sentence
   fits together: "a" and "the", "that", "which" and "who", and the verb.
   Start a docstring or a paragraph with a sentence, not a phrase and a colon.
2. **Do not stack clauses.** "Each entry the plan was not read whole at" makes
   the reader work out where each clause ends. Write "Each entry at which the
   plan was not read in full."
3. **Use words in their everyday sense.** Prose here has drifted into private
   senses that a newcomer cannot guess. Write "returns" and "result", not
   "answers" and "answer"; "review", not "read" as a noun; "treats as", not
   "reads as"; "enforces", not "holds"; "still applies", not "stands";
   "applies to", not "reaches"; "less than", not "under"; and "bypasses", not
   "writes past". Name the rule or the exception you mean instead of calling it
   a "floor" or a "door". When the project needs a term of its own, define it
   where it first appears.
4. **Make one point per sentence.** Put the subject and its verb early and
   close together. When a sentence needs a semicolon, a dash or a second
   parenthesis, split it. Keep a cause and its consequence in one sentence
   where they fit: "One step for all agents keeps the last MAC digit worth the
   same amount whatever the agent", not three sentences joined by "So".
5. **State the reason in words.** An item id, a pull request number or a
   section name can follow as a pointer, but the sentence must make sense
   without it.
6. **Say who does what.** Make each "it", "this" and "that" point at a noun the
   reader can find.
7. **Plain is not longer.** Say each thing once, where the reader needs it.
   Cut words that add nothing. Keep every fact where its own reader will look
   for it: in the paragraph, in the note for developers of a `docs/MODEL.md`
   section, or in the item. A unit, a value, an equation, a condition, an
   exception and a citation are facts. Moving or restating one never changes
   its value.
8. **Read it aloud.** If you would not say it that way to a colleague, rewrite
   it.

**Five patterns that make prose read as machine-written.** The points above
catch prose that is too compressed. These five catch the opposite failure:
padding that sounds careful and adds nothing. The project owner judged
`docs/MODEL.md` to read "like the worst kind of AI slop" on 2026-11-02 because
of them (`PL-ZT47`).

1. **A tautological aside.** A clause restates what its sentence already
   says: "The naming is Hendrickx and De Wolf's, which is the field's naming."
   Delete it. Where it carries a real fact, make that fact a sentence.
2. **A contrast nobody claimed.** "X, not Y" and "rather than Y" reject an
   option no reader proposed. State the positive claim. Keep a contrast only
   where a reader would otherwise assume Y.
3. **Narration about the text itself.** The sentence describes how the
   document records, sources or decides something, instead of the subject:
   "it is recorded at that depth", "the pages above are what the citation is
   being used for". Give the citation with its page numbers and stop. Who
   supplied a source, and how a choice was reached, belong in the item file.
4. **A defensive scope statement.** The sentence says what is not relied on,
   against an objection nobody raised: "no page beyond them is relied on
   here". Delete it. Where a reader would plausibly assume a source was used,
   say once that it was not, as a limitation.
5. **A table cell or paragraph that has grown into an essay.** Prose ordinals
   ("First", "Second" through "Sixth") or several separate points inside one
   table cell mean the content wanted to be a list. Move it to a numbered list
   or a short section, and leave the cell one sentence and a pointer.

Before, from `docs/MODEL.md` on 2026-11-02: "The naming is Hendrickx and De
Wolf's, which is the field's naming. They set out the gas-phase cascade and the
symbols F_D, F_I and F_A on pp. 161-162. [...] The project owner supplied this
source, and it is recorded at that depth. The pages above are what the
citation is being used for, and no page beyond them is relied on here."

After: "Symbols and the gas-phase cascade (F_D, F_I, F_A) follow Hendrickx and
De Wolf (pp. 161-162)." The full citation follows unchanged, and the last two
sentences go.

**A pull request title names the change plainly and briefly.** The title
becomes the squash commit's subject, the one line of `main`'s history that a
reader sees for the change. After the item ids that the `pr-title` check
requires, write a short phrase rather than a whole sentence: what the change
does, to what, and the reason when it fits. Use names a reader of the
repository already knows, such as a CI job, a check or a panel, not a term
coined while building the change. Give each number the thing it counts. Do not
describe the hoped-for effect in loose words instead of the change. When a
branch closes several items, name what they change together.

**Match the code around you, not its prose.** Copy the structure, naming and
idiom of the code you are working in. Much of the existing prose here breaks
the points above, so do not copy its sentences. Write each sentence you add or
change plainly, even when the text around it is dense. Rewriting sentences you
did not need to touch is work for its own item, in the `prose-quality`
feature. The exception is the copy editor at close-out, which may also rewrite
the paragraph or table row on each side of a passage you changed (`PL-22T5`).

This rule decides how a text is worded and ordered, and what it leaves out. The
safety-critical standard in `CLAUDE.md` and `.claude/rules/sources-and-docstrings.md`
decides which facts a docstring, an error message or a displayed value must give,
and this rule never cuts one. `.claude/rules/instruction-writing.md` decides the
shape of a reply. Code, commands, paths and quoted output stay exactly as they are.

## Three examples from this repository

Before: "Refuse a volume or tissue:gas coefficient whose capacity is under the
agent held."

After: "Reject a volume or tissue:gas partition coefficient that would make the
tissue's capacity less than the amount of agent it already holds."

Before: "The fresh gas admitted over the step, and as much circuit gas
exhausted. In circuit volumes it is the step in time constants, dt/tau, formed
without the time constant, which overflows to `inf` below about 2e-306 L/min in
a 6 L circuit."

After: "`admitted_gas_l` is the volume of fresh gas that enters the circuit
during the step. The same volume of circuit gas leaves through the exhaust.
Dividing `admitted_gas_l` by the circuit volume gives the step's length in time
constants, dt/tau. The code does not compute tau first, because tau overflows
to `inf` when the fresh gas flow is below about 2e-306 L/min in a 6 L circuit."

The project owner judged three versions of one pull request title, on
`#1523`, on 2026-10-17:

- Too cryptic: "PL-ZWQS: give the first CI part 2 of every 5 ordinary tests".
  A reader cannot tell what a "CI part" or an "ordinary test" is, or what the
  2 and the 5 count.
- Too conversational: "PL-ZWQS: make CI's two test jobs finish at about the
  same time". It describes a hoped-for effect and does not say what changed.
- Plain: "PL-ZWQS: rebalance the CI test split to offset part 1's lint steps".
  It names the change, what it changes and why.

The writing rule ends here, and the prose to review follows.

 9076 | 34. Take Blender's window management as the model for the interface. The
 9077 |     application window is divided into resizable, modular areas, and each area
 9078 |     holds one view. Task-oriented layout presets let the learner switch between
 9079 |     layouts, customize them and save them.
 9080 | 
 9081 |     *Requested by the project owner, 2026-09-12*. The request named four
 9082 |     properties: resizable windows, modular views, presets for tasks, and
 9083 |     presets that the user can customize and save, rather than a fixed set
 9084 |     shipped with the application.
 9085 | 
 9086 |     *Why Blender specifically, and what is worth copying.* Blender's window
 9087 |     system is **tiling**, not floating. The window is subdivided into resizable
 9088 |     areas that do not overlap, and each area hosts one view. The user splits
 9089 |     and joins areas from their corners and borders. Areas are grouped into
 9090 |     **Workspaces**. Workspaces are presented as tabs, and each one is geared to
 9091 |     a task. The user can reorder, duplicate and delete them. A layout persists
 9092 |     when it is saved into the startup file. The tiling half earns its place
 9093 |     here on merit, not on taste. A tiled layout has no overlapping or hidden
 9094 |     panels. On this application's dashboard, a covered value is a misread
 9095 |     value, and `CLAUDE.md`'s standard treats a misread value as a safety
 9096 |     failure rather than an inconvenience. See the Blender Manual, "Interface →
 9097 |     Window System → Areas" and "→ Workspaces".
 9098 | 
 9099 |     *The vocabulary is Blender's, and it is the concept rather than a
 9100 |     resemblance* (project owner, 2026-09-16: "the workspace/area concept ...
 9101 |     is what I want to implement"). The terms were read at the source. The
 9102 |     manual's "Areas" and "Workspaces" pages were supplied directly, because the
 9103 |     session egress proxy refused `docs.blender.org` when this was written,
 9104 |     though the host answered a probe on 2026-09-26 (`PL-M701`). This project uses
 9105 |     three terms, and two of them are adopted from Blender rather than invented:
 9106 | 
 9107 |     - An **Area** is a rectangle that reserves screen space. It holds one
 9108 |       thing and nothing else, and areas never overlap.
 9109 |     - A **View** is what occupies an area. The view is the part that has the
 9110 |       functionality. Item 36 is the catalogue of views.
 9111 |     - A **Workspace** is a set of areas that contain views. Each workspace is
 9112 |       geared to a task, and the user switches between workspaces as tabs.
 9113 |       Blender puts the tabs in the Topbar and saves workspaces in the file. It
 9114 |       also lets a custom set of workspaces become the defaults.
 9115 | 
 9116 |     **Docking** is the manual's word for the corner-drag operations. The set of
 9117 |     operations is larger than "split and join". Dragging from an area corner
 9118 |     can join two areas, split one, or do both at once. Dragged into the middle
 9119 |     of a second area, it *replaces* that area. Areas can also swap. Adjacent
 9120 |     areas swap through the border's Area Options, and any two areas in a window
 9121 |     swap through Ctrl-LMB from a corner. Resizing is a border drag. Modifier
 9122 |     keys snap the border, or move aligned borders together with it.
 9123 | 
 9124 |     **Two precedents worth copying, both from the source.** Blender refuses to
 9125 |     delete the last workspace. It enforces this minimum structurally rather
 9126 |     than by a warning, which is the same shape `PL-WLWY` settled for the
 9127 |     minimum display. A workspace also carries *settings*, not only a layout.
 9128 |     Pin Scene makes activating a workspace switch back to the scene that the
 9129 |     workspace remembers. The equivalent here is a workspace that pins which
 9130 |     **run** it shows. That is exactly what a broken-out window needs in order
 9131 |     to name its run.
 9132 | 
 9133 |     *Tiled first, with break-out into a separate window* (project owner,
 9134 |     2026-09-15). **Scoped across two releases on 2026-09-16**. § "v0.6.0 - the
 9135 |     layout is the reader's" (ratified 2026-09-16) builds the tiled no-overlap
 9136 |     invariant, the View contract, the registry, workspaces, persistence and the
 9137 |     unconditional region. Break-out occupied the release after it,
 9138 |     "the second screen", until it came off the timeline on 2026-09-26 (see
 9139 |     below). The split costs nothing structural. Break-out would otherwise force
 9140 |     a rewrite of two things, and v0.6.0 builds both of them. First, the
 9141 |     serialized layout root carries a set of windows from version 1. Second, the
 9142 |     unconditional region is built in the per-window shape that the next
 9143 |     paragraph settles. Together, the two halves build the no-overlap invariant
 9144 |     above plus break-out. Break-out lets an area be taken into **its own
 9145 |     top-level window**, which is itself a full window with its own areas. The
 9146 |     Blender Manual's "Areas" page documents this as *View > Duplicate Area into
 9147 |     New Window*, or Shift-LMB on an area's splitter widget. The manual
 9148 |     describes the result as a fully functional window that belongs to the same
 9149 |     running instance and is useful across multiple monitors. Every window is
 9150 |     then tiled, so nothing inside a window covers anything else in it.
 9151 | 
 9152 |     *What is refused is silent occlusion, not floating* (project owner,
 9153 |     2026-09-15, correcting this paragraph's first form). **Floating is
 9154 |     deliberately not foreclosed.** The option to take a tiled area out into a
 9155 |     floating one is wanted later. This milestone simply does not build it yet.
 9156 |     The first version of this paragraph recorded floating panels as
 9157 |     "not admitted". That was a permanent refusal, and it was the writing session's
 9158 |     overreach rather than a decision anybody took. Tiled first is only the
 9159 |     order of work. It is not a rule that floating is never allowed.
 9160 | 
 9161 |     The safety argument actually supports a narrower rule, and that rule
 9162 |     outlives whichever mechanism arrives: **nothing may cover a value the
 9163 |     display is required to show while the application still believes it is
 9164 |     showing it.** A floating panel over the dashboard is one way to cover such
 9165 |     a value. A broken-out window dragged back over the main window is another.
 9166 |     That is why the constraint belongs to the display rather than to a window
 9167 |     type. It is stated once, instead of being argued again for each mechanism.
 9168 |     **It is settled** (`PL-WLWY`, project owner, 2026-09-15), in
 9169 |     `docs/MODEL.md` § "Minimum displayed outputs" ->
 9170 |     "What this list requires once the layout is the reader's". That list now
 9171 |     divides into three parts.
 9172 |     The first is an **unconditional** set that no workspace may remove and
 9173 |     nothing may cover. This set is stated as a test rather than a list. It has
 9174 |     an invariant tier and a tier instantiated for each modelled substance. So
 9175 |     the inhaled agent's concentrations and MAC are today's instance and not a
 9176 |     permanent requirement (project owner, 2026-09-16). The second part is an
 9177 |     **accounting** set that must stay reachable rather than simultaneously
 9178 |     visible. The third part is **conditional** obligations, which apply to a
 9179 |     surface only when that surface is shown. So removing a chart removes no
 9180 |     required value, because the numbers never left. The unconditional set sits
 9181 |     outside the area system, and keeping it there is the guarantee that v0.6.0
 9182 |     has to build. **What a second top-level window owes that set is settled
 9183 |     too** (project owner, 2026-09-16, ratified, answering `PL-W54S`, chosen
 9184 |     over that item's own two live readings). Every top-level window carries
 9185 |     the *invariant* tier and the name of the run it shows. The *per-substance*
 9186 |     tier appears once, in a main window that cannot be closed while any other
 9187 |     window is open. The two tiers are unconditional for different reasons, and
 9188 |     those reasons carry over to a second window differently. That is why the
 9189 |     tiers are allocated to windows differently. `docs/MODEL.md` carries the
 9190 |     argument, the two readings it refused, and the limit on which occlusion
 9191 |     any application can observe. This decision is recorded before break-out
 9192 |     is built, because it decides the shape in which v0.6.0 builds the region.
 9193 |     Any later floating mechanism must comply with the occlusion rule, rather
 9194 |     than being ruled out ahead of time. The division of the list is recorded
 9195 |     as **a stepping stone**. It is deliberately the rigid version while the
 9196 |     layout apparatus is built, and it is expected to be revisited as the
 9197 |     apparatus matures. The occlusion rule is the part that must survive a
 9198 |     revision.

 9200 |     *The licence constraint, and it runs the opposite way for the two kinds of
 9201 |     source.* `docs/interface-provenance.md` is the record. It holds the study
 9202 |     protocol, what was read, what this project adopts and what it deliberately
 9203 |     does differently. A session building the layout should start there. In
 9204 |     short, Blender's source files are GPL-2.0-or-later (the work as a whole is
 9205 |     GPL-3.0-or-later), and this project is Apache-2.0. So **reading the source
 9206 |     is unrestricted**, because GPLv2 s.0 puts activities other than copying,
 9207 |     distribution and modification outside the licence's scope. Copying,
 9208 |     translating or porting the source into this tree is restricted, and doing
 9209 |     so would make the stated licence wrong. But the constraint that matters in
 9210 |     practice is the other one. The **Blender Manual and Developer
 9211 |     Documentation, including the Human Interface Guidelines, are CC-BY-SA
 9212 |     4.0**. Pasting their prose *is* copying, whereas reading source is not.
 9213 |     **Paraphrase and cite, and never paste** (`PL-P5QX`). The design rationale
 9214 |     that this project wants is in the Developer Docs and the HIG, not in the
 9215 |     Manual, which documents behaviour for users. Qt supplies the primitives
 9216 |     directly in any case: nested `QSplitter` for the tiling, and a project file
 9217 |     for a named preset.
 9218 | 
 9219 |     *The layout is a nested-splitter tree, and Blender's own shipped layouts are
 9220 |     what settled it* (`PL-3J2P`, decided 2026-09-16 on the research that the
 9221 |     project owner asked for before the decision was fixed). The question was
 9222 |     how to store the layout. One option was Blender's shared-vertex graph, in
 9223 |     which each area names four corner points and neighbouring areas share
 9224 |     them. The other option was nested splitters. The question was settled by
 9225 |     measurement rather than argument, against a threshold written down first.
 9226 |     **Across all 32 workspaces Blender ships** (11 defaults and 21 in its five
 9227 |     application templates), **none uses an arrangement a splitter tree cannot
 9228 |     express**. Exactly one contains a four-way junction. At that junction the
 9229 |     tree must split one of the two crossing borders into two handles. The two
 9230 |     behaviours that a tree cannot express are both opt-in. Extend-drag is the
 9231 |     Shift key on the border drag, and snap-merge is a separate operator on the
 9232 |     border's right-click menu.
 9233 | 
 9234 |     One supporting argument did **not** survive the research, and the decision
 9235 |     is recorded without it. A splitter tree is **strictly less expressive**
 9236 |     than Blender's representation. Five full-span splits and one ordinary join
 9237 |     reach a five-area pinwheel, and no sequence of full-span cuts can produce
 9238 |     that pinwheel. So the tree is chosen in the knowledge that it gives
 9239 |     something up. There are four grounds for the choice. Blender's own
 9240 |     designers never used the extra expressiveness in 32 shipped layouts. This
 9241 |     audience picks a workspace rather than authoring one. The tree's limit
 9242 |     shows up as a **join being unavailable** rather than as a wrong value. And
 9243 |     a planar subdivision is owned by one person forever.
 9244 |     `docs/interface-provenance.md` carries the count, the method, the
 9245 |     construction and the condition under which this decision reverses.
 9246 | 
 9247 |     *The container sits behind a layout model of this project's own*
 9248 |     (`PL-C842`, recommended 2026-09-16 with the review of Blender behind it,
 9249 |     and the owner delegated the architecture call). The negative half was
 9250 |     settled by measurement, and the research did not overturn it.
 9251 |     `QSplitter.saveState()` returns 35 opaque bytes that carry sizes and a
 9252 |     child count. It **cannot record which view occupies which pane**, and that
 9253 |     mapping is the whole of what a named workspace is. Restoring a three-child
 9254 |     state into a two-child splitter **returns `True`** with sizes `[318, 318]`
 9255 |     rather than failing. That last behaviour is disqualifying on this file's
 9256 |     own standard, which prefers an obvious failure to a plausible-looking wrong
 9257 |     result.
