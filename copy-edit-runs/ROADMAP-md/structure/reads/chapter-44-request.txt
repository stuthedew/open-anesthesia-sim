# Write plainly

**Resident, with no `paths:`.** It applies whenever a session writes prose. A
path scope would miss item briefs, commit messages, pull request bodies and
replies, because no read comes before them. The project owner asked for this
rule on 2026-10-17, and `PL-8ZTQ` has the measurement and the sources behind
each point.

Write all prose that a person will read in plain English: docstrings, comments,
error messages, documents, rules, item briefs, commit messages, pull request
titles and bodies, replies, and every question or review request sent to the
project owner, including each field of the line `bin/docket arm` prints. In
those, say what changes for the owner or a learner, and never name a test,
check or tool by its internal name (project owner, 2026-11-02, `PL-BGN1`).
Write for the readers that the table below names for that kind of text. They
should understand each sentence the first time they read it (project owner,
2026-11-02, ratified, `PL-H76S`).

The two `README.md` rows are the readers that `README.md` § "What it is for"
names. `docs/releases/` has no row, because `bin/docket release` writes each
note from item titles, and an edit there would make a note disagree with its
item. `tools/new_prose.py` reads this table. It prints a changed file's passages
for the copy editor only when a row names that file, and it gives each passage
that row's readers. A new row therefore brings the files it names into the
review with no other change.

**Write what the reader needs to act on, and stop.** Find the reader and what
they will do with the text in the table above. Put what they see first, then
what it means for them, then why. Move each reason, derivation, test name and
piece of history that they do not act on to where its own reader looks, or cut
it. Decision history goes in the item. In `docs/MODEL.md`, the rest goes in a
note for developers at the end of the section it came from, a paragraph that
opens with "**For developers.**" That note may name the tests for the paragraphs
directly above it (`PL-W8FL`). That detail stays in `docs/MODEL.md`, because the
document must specify the numerical method (`PL-TZ7R`). State a model limitation
only where it could change what a clinician concludes from a displayed value
(`PL-BS6N`).

**Give a chosen value its reason from a record.** Where a docstring or a
comment gives a chosen value, such as a tolerance or a limit, say what the
value does, why it is this number, and what changing it would do. In
`docs/MODEL.md`, say it in the note for developers. Take each answer from the
code or test that uses the value, or from a cited record. When the reason is
not at hand, trace the value's history first, with `git log -S` and the items.
Search for the value as the code writes it. The step-size test's 0.5% tolerance,
removed in `PL-VXM0`, was `5e-3` in `tests/reference/test_sevo_patient.py`, and
`git log -S 5e-3` finds the commit that first set it. When the trace finds no
reason, file an item for the missing record, and say in the text what the trace
found. Never state a reason that no record holds.

1. **Write whole sentences.** Keep the small words that show how a sentence
   fits together: "a" and "the", "that", "which" and "who", and the verb.
   Start a docstring or a paragraph with a sentence, not a phrase and a colon.
2. **Do not stack clauses.** "Each entry the plan was not read whole at" makes
   the reader work out where each clause ends. Write "Each entry at which the
   plan was not read in full."
3. **Use words in their everyday sense.** Prose here has drifted into private
   senses that a newcomer cannot guess. Write "returns" and "result", not
   "answers" and "answer"; "review", not "read" as a noun; "treats as", not
   "reads as"; "enforces", not "holds"; "still applies", not "stands";
   "applies to", not "reaches"; "less than", not "under"; and "bypasses", not
   "writes past". Name the rule or the exception you mean instead of calling it
   a "floor" or a "door". When the project needs a term of its own, define it
   where it first appears.
4. **Make one point per sentence.** Put the subject and its verb early and
   close together. When a sentence needs a semicolon, a dash or a second
   parenthesis, split it. Keep a cause and its consequence in one sentence
   where they fit: "One step for all agents keeps the last MAC digit worth the
   same amount whatever the agent", not three sentences joined by "So".
5. **State the reason in words.** An item id, a pull request number or a
   section name can follow as a pointer, but the sentence must make sense
   without it.
6. **Say who does what.** Make each "it", "this" and "that" point at a noun the
   reader can find.
7. **Plain is not longer.** Say each thing once, where the reader needs it.
   Cut words that add nothing. Keep every fact where its own reader will look
   for it: in the paragraph, in the note for developers of a `docs/MODEL.md`
   section, or in the item. A unit, a value, an equation, a condition, an
   exception and a citation are facts. Moving or restating one never changes
   its value.
8. **Read it aloud.** If you would not say it that way to a colleague, rewrite
   it.

**Five patterns that make prose read as machine-written.** The points above
catch prose that is too compressed. These five catch the opposite failure:
padding that sounds careful and adds nothing. The project owner judged
`docs/MODEL.md` to read "like the worst kind of AI slop" on 2026-11-02 because
of them (`PL-ZT47`).

1. **A tautological aside.** A clause restates what its sentence already
   says: "The naming is Hendrickx and De Wolf's, which is the field's naming."
   Delete it. Where it carries a real fact, make that fact a sentence.
2. **A contrast nobody claimed.** "X, not Y" and "rather than Y" reject an
   option no reader proposed. State the positive claim. Keep a contrast only
   where a reader would otherwise assume Y.
3. **Narration about the text itself.** The sentence describes how the
   document records, sources or decides something, instead of the subject:
   "it is recorded at that depth", "the pages above are what the citation is
   being used for". Give the citation with its page numbers and stop. Who
   supplied a source, and how a choice was reached, belong in the item file.
4. **A defensive scope statement.** The sentence says what is not relied on,
   against an objection nobody raised: "no page beyond them is relied on
   here". Delete it. Where a reader would plausibly assume a source was used,
   say once that it was not, as a limitation.
5. **A table cell or paragraph that has grown into an essay.** Prose ordinals
   ("First", "Second" through "Sixth") or several separate points inside one
   table cell mean the content wanted to be a list. Move it to a numbered list
   or a short section, and leave the cell one sentence and a pointer.

Before, from `docs/MODEL.md` on 2026-11-02: "The naming is Hendrickx and De
Wolf's, which is the field's naming. They set out the gas-phase cascade and the
symbols F_D, F_I and F_A on pp. 161-162. [...] The project owner supplied this
source, and it is recorded at that depth. The pages above are what the
citation is being used for, and no page beyond them is relied on here."

After: "Symbols and the gas-phase cascade (F_D, F_I, F_A) follow Hendrickx and
De Wolf (pp. 161-162)." The full citation follows unchanged, and the last two
sentences go.

**A pull request title names the change plainly and briefly.** The title
becomes the squash commit's subject, the one line of `main`'s history that a
reader sees for the change. After the item ids that the `pr-title` check
requires, write a short phrase rather than a whole sentence: what the change
does, to what, and the reason when it fits. Use names a reader of the
repository already knows, such as a CI job, a check or a panel, not a term
coined while building the change. Give each number the thing it counts. Do not
describe the hoped-for effect in loose words instead of the change. When a
branch closes several items, name what they change together.

**Match the code around you, not its prose.** Copy the structure, naming and
idiom of the code you are working in. Much of the existing prose here breaks
the points above, so do not copy its sentences. Write each sentence you add or
change plainly, even when the text around it is dense. Rewriting sentences you
did not need to touch is work for its own item, in the `prose-quality`
feature. The exception is the copy editor at close-out, which may also rewrite
the paragraph or table row on each side of a passage you changed (`PL-22T5`).

This rule decides how a text is worded and ordered, and what it leaves out. The
safety-critical standard in `CLAUDE.md` and `.claude/rules/sources-and-docstrings.md`
decides which facts a docstring, an error message or a displayed value must give,
and this rule never cuts one. `.claude/rules/instruction-writing.md` decides the
shape of a reply. Code, commands, paths and quoted output stay exactly as they are.

## Three examples from this repository

Before: "Refuse a volume or tissue:gas coefficient whose capacity is under the
agent held."

After: "Reject a volume or tissue:gas partition coefficient that would make the
tissue's capacity less than the amount of agent it already holds."

Before: "The fresh gas admitted over the step, and as much circuit gas
exhausted. In circuit volumes it is the step in time constants, dt/tau, formed
without the time constant, which overflows to `inf` below about 2e-306 L/min in
a 6 L circuit."

After: "`admitted_gas_l` is the volume of fresh gas that enters the circuit
during the step. The same volume of circuit gas leaves through the exhaust.
Dividing `admitted_gas_l` by the circuit volume gives the step's length in time
constants, dt/tau. The code does not compute tau first, because tau overflows
to `inf` when the fresh gas flow is below about 2e-306 L/min in a 6 L circuit."

The project owner judged three versions of one pull request title, on
`#1523`, on 2026-10-17:

- Too cryptic: "PL-ZWQS: give the first CI part 2 of every 5 ordinary tests".
  A reader cannot tell what a "CI part" or an "ordinary test" is, or what the
  2 and the 5 count.
- Too conversational: "PL-ZWQS: make CI's two test jobs finish at about the
  same time". It describes a hoped-for effect and does not say what changed.
- Plain: "PL-ZWQS: rebalance the CI test split to offset part 1's lint steps".
  It names the change, what it changes and why.

The writing rule ends here, and the prose to review follows.

 7729 | 2. **Freeze and record** the debt list in that milestone's own section, as
 7730 |    item ids, on the day it was frozen. The list freezes on the later of two days:
 7731 |    the day the milestone is scoped, and the day the milestone before it ships.
 7732 | 3. **Clear** it before implementation of the milestone begins. Each item ends
 7733 |    `done`, or `dropped` with its reason, or **deferred to a later gate** on
 7734 |    the terms below. **Sweep the frozen list for staleness first** (project
 7735 |    owner, 2026-09-17, ratified, chosen over a second `verify:`-style field
 7736 |    recording a fault test beside each fix test, and over leaving the sweep to
 7737 |    whoever next noticed). A `verify:` command is specified as one that fails
 7738 |    before the work and passes after it. So it tests for the presence of the
 7739 |    fix, and never for the presence of the fault. An entry whose defect no
 7740 |    longer reproduces therefore fails forever and looks like outstanding work.
 7741 |    One measured pass found 12 of 134 open items dead and 31 more overtaken,
 7742 |    32% in all. Nothing in the project noticed this, and nothing can. A churn
 7743 |    advisory was built and measured against that pass's verdicts. It was
 7744 |    rejected because `partly` churns *less* than `yes` (`PL-LKGL`). Staleness
 7745 |    is a judgment, which is why this is a beat and not a check. Read each
 7746 |    frozen entry against the tree. Drop what no longer reproduces, with its
 7747 |    reason. Correct the briefs that overstate what is left. Do all this before
 7748 |    spending a session on any of them.
 7749 |    **File the pass as its own item under `feature: gate-staleness-sweep`. Do
 7750 |    not name a standing one here.** Any item named here is an item that can
 7751 |    close. The next gate's session then looks that item up and finds it
 7752 |    `done`. That is what happened to `PL-6ZQY`. It closed on 2026-09-19, two
 7753 |    days before Gate 2 froze on a list it had never seen (`PL-D8KW`). An
 7754 |    instruction to file an item cannot go stale the way a pointer to one item
 7755 |    does.
 7756 | 
 7757 |    **The third disposition, and the terms that make it legitimate** (project
 7758 |    owner, 2026-09-21, ratified, over leaving each milestone's own bullet to be
 7759 |    read at its own cut). An entry may be *deferred to a later gate* instead of
 7760 |    cleared. The release then ships without it. That is allowed only when all
 7761 |    three of these conditions hold:
 7762 | 
 7763 |    - § "The gate is a snapshot, not a moving target" permits the deferral.
 7764 |      That means the deferral **says so and says why**. The entry's item
 7765 |      carries `deferred-from: vX.Y.Z - <why>`, naming this gate. That field is
 7766 |      the one record that every reader of the gate reads (`PL-8QMD`, project
 7767 |      owner, 2026-10-11, ratified, over the deferral group headings this
 7768 |      section used to carry). The gate section may also set out the decision
 7769 |      behind the deferral at any length.
 7770 |    - The deferral **lands in a named later gate**, which is the next one. The
 7771 |      next gate's freeze carries every open entry that this list deferred,
 7772 |      debt or not, taken from what `bin/docket gate` prints. This matters
 7773 |      because an entry deferred to nowhere is what holds a release open
 7774 |      (`PL-S5Q9`). The field names the gate the entry leaves, not the one it
 7775 |      reaches, as `PL-WD5Z` decided. That is enough, because the next freeze
 7776 |      is always the one that takes the entry.
 7777 |    - The entry **stays written on the frozen list**, because removing it is
 7778 |      the renegotiation the freeze exists to prevent.
 7779 | 
 7780 |    A `safety`- or `science`-classed entry may take this route only when its
 7781 |    deferral also records that its hazard is **not live**. That must be
 7782 |    checked against the tree rather than asserted. It is recorded in the
 7783 |    field's reason or in the gate section.
 7784 | 
 7785 |    **Stated here rather than in each definition of done**, because it
 7786 |    recurs. Gate 1's last entry, `PL-WZVZ`, is deferred to Gate 2 on exactly
 7787 |    these terms. Yet v0.5.0's bullet admits only `done` or `dropped`. So a
 7788 |    session running that cut would have had to choose between two things. It
 7789 |    could drop a `safety`-classed entry whose hazard is real but not yet live,
 7790 |    or it could hold the release. `PL-F0L8` records one occasion when the
 7791 |    bullet was already treated as exhaustive, and `dropped` was chosen to stay
 7792 |    inside it. Gate 2 freezes the day v0.5.0 ships and inherits that entry. So
 7793 |    a gate with a deferral in it is the normal case, not something special to
 7794 |    this gate. This would be an instance rather than a rule only if no later
 7795 |    gate ever deferred an entry, and Gate 2 already falsifies that. Completed
 7796 |    milestones' bullets are left as written. They record conditions those
 7797 |    releases met, and editing a satisfied condition is the wider change
 7798 |    (`PL-Y949`).
 7799 | 4. **Implement** the milestone. A finding made while clearing or implementing
 7800 |    goes to the next gate, with two exceptions. It re-enters this gate if the
 7801 |    problem it describes predates the freeze (per § "The gate is a snapshot"
 7802 |    above). It also re-enters this gate if it is `P0`/`safety`/`science`.
 7803 | 
 7804 | A scoped milestone carries its gate heading from the day it is scoped, empty
 7805 | until the freeze. A milestone without one has not been scoped, whatever else
 7806 | has been written about it.
 7807 | 
 7808 | **Why the later of the two days** (project owner, 2026-10-03, ratified, over
 7809 | keeping scoping as the trigger with exceptions recorded against it,
 7810 | `PL-KKRP`). A gate contains the findings of the milestone before it. So a list
 7811 | frozen before that milestone ships contains none of those findings, and sends
 7812 | them to the gate after. A list frozen before its own milestone is scoped has
 7813 | no section to be recorded in. Nothing in this rule is open to renegotiation.
 7814 | The timeline fixes the freeze date, not whoever next opens the section. Every
 7815 | gate frozen under this cadence froze on the later day. Gate 1 froze on
 7816 | 2026-09-06, the day v0.5.0 was scoped. v0.4.0 had shipped the day before.
 7817 | Gate 2 froze on 2026-09-21, the day v0.5.0 shipped. v0.6.0 had been scoped
 7818 | two releases early, on 2026-09-16. That freeze was recorded at the time as an
 7819 | exception to scoping as the trigger (project owner, 2026-09-16, ratified while
 7820 | scoping v0.6.0). It is the instance that showed the rule's shape. The
 7821 | timeline's rows for Gates 3 and 4 were already written on the ship day.
 7822 | v0.4.26 was counted as a second exception. But it was a patch on the `v0.4.x`
 7823 | track, and a patch freezes no gate, so it says nothing about the trigger.
 7824 | 
 7825 | Which beat is due is computed, not remembered. `bin/docket wave` reads the
 7826 | version, the timeline above, the milestone sections and the frozen list that
 7827 | each section records. It reports the current step and the beat that leaves
 7828 | that step. It reports only what those files decide. It does not report
 7829 | whether a gate should open early, or whether what is written beside a step is
 7830 | still true.
 7831 | 
 7832 | **A gate does not get a version of its own. Its work ships as it clears.**
 7833 | Cleared gate work ships in patch releases on the preceding milestone's track:
 7834 | `v0.4.x` while Gate 1 drained, and `v0.5.x` while Gate 2 does. A session cuts
 7835 | one whenever it judges the finished work worth releasing. The gated
 7836 | milestone's own number is reserved for the capability boundary that its scope
 7837 | crosses, per § "Versioning decision". That milestone's release notes then
 7838 | carry its own scope. That is what a milestone should carry when its debt was
 7839 | paid down as it went.
 7840 | 
 7841 | **This records the practice rather than changing it** (project owner,
 7842 | 2026-09-27, `PL-LPH9`). The sentence that used to be here said that no
 7843 | interim release is cut partway through clearing. It told sessions to decline
 7844 | `docket release`'s offer, or else see the gate work scatter across patch
 7845 | releases. Every gate has been worked the other way. Gate 0 closed across the
 7846 | v0.2.6 to v0.3.0 patch series. At v0.4.32 on 2026-09-20, `bin/docket wave`
 7847 | treated 172 of the 175 entries that Gate 1 then contained as clear. v0.5.1
 7848 | through v0.5.14 shipped 67 of Gate 2's 190. **Since 2026-09-27 the occasion
 7849 | for a cut is a feature finishing**. A session cuts a release with what is in
 7850 | it, and the project owner pushes the tag. That is the instance the judgment
 7851 | currently turns on. It is dated so that a later reader can tell it apart from
 7852 | the rule.
 7853 | 
 7854 | Gate 0 is the single exception. It was released as the *minor* v0.3.0, for
 7855 | the reason recorded under § "Versioning decision". It is exempt because it
 7856 | holds the backlog inherited from before this mechanism existed. Every later
 7857 | gate holds one milestone's findings and is ordinary maintenance. Ordinary
 7858 | maintenance ships in patches and takes no number of its own.
 7859 | 
 7860 | ### Debt inside the milestone's own scope
 7861 | 
 7862 | **Debt that the milestone itself exists to clear is cleared *by* it, not
 7863 | before it.** This carve-out is necessary rather than convenient. v0.4.0 was
 7864 | scoped in part *because* six safety, science, defect and perf items were all
 7865 | symptoms of the same thing. A rule that required them to be cleared before the
 7866 | milestone that clears them would have no order that satisfies it.
 7867 | 
 7868 | The test is whether the item appears in the milestone's "Required scope". If
 7869 | it does, it is milestone work. The frozen gate lists it under a heading that
 7870 | says so, and the gate is open when everything *outside* the milestone's scope
 7871 | is clear. If it does not appear there, it is cleared first, whatever it is
 7872 | about.
 7873 | 
 7874 | This does not weaken the `safety`/`science` re-entry rule above. Such an item
 7875 | inside the scope still cannot be deferred. It simply cannot be finished
 7876 | earlier than the work it is part of, and the milestone's definition of done is
 7877 | what enforces it.
 7878 | 
 7879 | ### Recording it
 7880 | 
 7881 | Record the frozen list in the milestone's own section here, as the ids of the
 7882 | items it had to clear. A gate that nobody wrote down gets renegotiated. The
 7883 | point of freezing the list is that it cannot be renegotiated.
 7884 | 
 7885 | **Record a deferral on the item, not here.** A debt item that the current gate
 7886 | neither places nor takes carries `deferred-from: vX.Y.Z - <why>`. The version
 7887 | is the milestone whose frozen list excuses the item. It is never the gate that
 7888 | the item goes to, because the next freeze takes every open debt item anyway.
 7889 | The reason states the grounds for the deferral, which is what a reader of the
 7890 | gate is owed. The command `bin/docket set <id>
 7891 | --deferred-from "..."` writes it. `bin/docket check` fails an open debt
 7892 | item that the current gate neither places nor defers, and its error message
 7893 | prints that command (`PL-WD5Z`). **A frozen entry deferred on § "The cadence"
 7894 | beat 3's terms carries the same field** (`PL-8QMD`). The entry stays on its
 7895 | list. The next freeze takes it whatever its classes, because `bin/docket gate`
 7896 | prints every open entry of the last frozen list beside the store's open debt.
 7897 | `bin/docket check` also fails an open frozen entry that is waiting on work
 7898 | outside the plan, unless the field defers it. Work is outside the plan when
 7899 | neither the entry's list nor the milestone's `Required scope` includes it, and
 7900 | the release train does not schedule it first. A section may state the grounds
 7901 | that its deferrals share, as v0.6.0's section does, but no tool reads that
 7902 | prose. Until `PL-WD5Z`, a deferral was an id named in a `###` subsection
 7903 | headed `Declined`, `Deferred` or `Sequenced`. Each way in which that second
 7904 | store disagreed with the items became an item of its own. Completed sections
 7905 | keep those subsections, because they are the record of that period.
 7906 | 
 7907 | **Do not write a deferred item's state or release beside it.** `bin/docket
 7908 | wave` prints each deferral of the current gate with its state and release,
 7909 | read from the store (`PL-B60Q`). A mark written by hand would only copy a
 7910 | field that the store already records.
