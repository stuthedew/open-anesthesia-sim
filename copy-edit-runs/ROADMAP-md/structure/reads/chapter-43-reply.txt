Outline:
- 7455: heading "Keeping the toolchain current".
- 7457-7458: lead. When a dependency or the interpreter changes, a scheduled run notices and the owner decides. Nothing upgrades on a schedule, and nothing gates on it.
- 7460-7467: why the run is needed. The project is multi-year, so every version constraint in `pyproject.toml` will eventually be wrong. `requires-python` admits two CPython minor versions, 3.14 and 3.15. CPython ships a new minor version each year. Flet is pre-1.0, and an upper bound excludes Flet 1.0. The dev tools have only lower bounds, so their behaviour changes underneath "the gate". The failure guarded against is not a stale pin. It is coming back after a gap to a tree that no longer builds, when the fixing upgrade is several versions wide and costs more than a hobby project will pay.
- 7469-7473: a real case, recorded in `pyproject.toml`. pydantic 2.12.4 began passing `prefer_fwd_module=` to `typing._eval_type`. CPython added that keyword between 3.14.0rc2 and 3.14.0 final. Parameter loading in the scientific core stopped working. It took one dependency, one patch version and one interpreter build.
- 7475-7477: "What notices". `.github/workflows/drift.yml` runs monthly and on demand. It asks two questions that `quality.yml` is "right not to ask", plus a third that runs weekly.
- 7479-7482: `dependencies` check. It checks the newest release that each bound in `pyproject.toml` allows, resolved with `uv sync --upgrade`. A failure means a dependency broke the project inside a range the project already accepts.
- 7483-7486: `interpreter` check. It checks the newest stable CPython, relaxing the upper bound on `requires-python` in the runner only. A failure means the next interpreter is not ready for the tree, or the tree is not ready for it.
- 7487-7490: `order` check. It runs the whole suite in shuffled order every Monday, using pytest-randomly with the date as the seed. A failure means a test passes only when another runs before it. The output names the seed that reproduces the failure (`PL-75D9`).
- 7492-7495: the workflow also prints what exists beyond the declared bounds, without failing. The reason it does not fail: crossing a major bound is a deliberate migration that CI should not attempt. This report is the only way anyone learns that a Flet 1.0 or a pydantic 3 is available.
- 7497-7503: "What does not happen". There are no automated dependency pull requests and no version-bump campaign. The current pins are correct "today" (no date given). The point is to know when a pin stops being correct, not to raise numbers on a schedule. Automated bumps were considered and rejected, on evidence the project cites about narrow versus broad automation. Broad automation builds up noise until people route around it, the failure that `PL-ZBJ0` records.
- 7505-7508: "Why it reports rather than gates". Nobody here controls the versions the workflow resolves. Gating would let an unrelated upstream release block the project's own work. A red run is news to act on when convenient, not a signal to stop.
- 7510-7513: "retired if it stops being news". `CLAUDE.md`'s retirement test applies: a check that fires every run without changing a decision is a defect in the check. If the workflow's failures become routine background that nobody acts on, delete the workflow rather than work around it.
