Outline:
- 743: Heading "Give update-armed its token, and renew it".
- 745–750: What the workflow does and why it needs a token. On every push to `main`, `.github/workflows/update-armed.yml` brings `main` into each armed pull request that `main` has moved past (`PL-S5MF`). The update needs a token that only the owner can make. An update made with the workflow's own token starts the pull request's checks in a state that requires approval, so the checks would wait for the owner. Until the secret exists, each run lists what it would have updated and changes nothing.
- 752: Lead "To make the token", done on the Mac.
- 754–757, step 1: Open the prefilled token form link. The link presets name=update-armed, a description, target_name=stuthedew, expires_in=366, contents=write, pull_requests=write and workflows=write. It opens Settings > Developer settings > Personal access tokens > Fine-grained tokens > Generate new token. The name, description, owner, 366-day expiry and permissions are already set.
- 758–759, step 2: Under Repository access, choose Only select repositories and pick `stuthedew/open-anesthesia-sim`. The link cannot set this.
- 760–762, step 3: Check that the repository permissions are exactly Contents, Pull requests and Workflows (each Read and write) and Metadata (Read-only). GitHub adds Metadata by itself.
- 763, step 4: Click Generate token and copy it. GitHub shows the token only once.
- 765: Lead "To store it".
- 767–768, step 5: On the repository's page, click Settings, then Secrets and variables > Actions under Security in the sidebar, then New repository secret.
- 769–774, step 6: Enter Name `UPDATE_BRANCH_TOKEN`, paste the token as the Secret and click Add secret. When this has worked, the secret is listed under Repository secrets. The command `gh secret set UPDATE_BRANCH_TOKEN --repo stuthedew/open-anesthesia-sim` does steps 5 and 6 and prompts for the value.
- 776–789: Why those permissions. GitHub's permission table lists only Pull requests for the update call (source: "Permissions required for fine-grained personal access tokens", docs.github.com). GitHub's reference page for the call ("Update a pull request branch") adds that a GitHub App must also be able to write the head repository's contents. That page does not say whether this applies to a token, so Contents is included now rather than found missing at the first update. Without Workflows, GitHub refuses an update that brings in a change to a workflow file. Mergify's app met that refusal when updating branches that were behind a workflow change (Mergifyio/mergify#5055). When GitHub refuses, the run turns red, and its summary names the permission that GitHub asked for.
- 791–793: To see it work, open Actions > update-armed after the next merge. The newest run's summary lists each armed pull request that the run read, and marks *updated* beside each one that it brought `main` into.
- 795–800: To renew it, make a new token the same way before its expiry date, or when runs turn red with HTTP 401. Paste it over the old value, either with the edit icon beside `UPDATE_BRANCH_TOKEN` on the same settings page or by running the `gh secret set` line again, which overwrites the old value. The 366 days is a choice, not a limit. A token that never expires saves the yearly renewal, but a leaked copy of it would then work for good.
