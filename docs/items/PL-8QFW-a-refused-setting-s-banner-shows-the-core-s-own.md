**Problem.** A refused setting's banner shows the core's own message, so a learner reads the setting by its Python name, as in 'Setting refused — delivered_concentration_percent exceeds the vaporizer maximum (50% requested, 5% maximum)'

**Found on 2026-11-22** while extending the approved-wording test to the states only an event brings up (`PL-4G79`). With isoflurane running, the delivered concentration handler given 50% shows this banner:

"Setting refused — delivered_concentration_percent exceeds the vaporizer maximum (50% requested, 5% maximum). The simulation is unchanged and still running its previous setting."

`refused_setting_notice` in `app/dashboard_frame.py` formats `REFUSED_SETTING_TEMPLATE` with the `SimulationConfigurationError` itself, and `core/validation.py` writes that message with the parameter's Python name, for a developer. `.claude/rules/plain-writing.md` says a string a learner reads holds no software term.

**Why it matters.** The banner is conditional text that a learner acts on. "delivered_concentration_percent" is readable, but it is a code name, and other settings' names may be less so. The value and the limit in the message are correct.

**Done when.** The banner names the setting in the learner's words (the dial's own label), and keeps the value and the limit. The developer's message stays available in the log or the exception. The approved-wording list records the new banner.

**Done 2026-11-23.** The banner now names the setting by its control's label, gives the value asked for and the limit, and says which limit refused it. With isoflurane running, the delivered concentration handler given 50% shows "Setting refused — the vaporizer setting cannot be 50.0%, because this agent's vaporizer delivers at most 5.0%. The simulation is unchanged and still running its previous setting." The sentence follows the shape of the stopped run's refusal ("the cardiac output setting cannot be changed on a stopped run, ..."). Each value is written exactly, as the core's message writes it (`shown`), rather than at the readout's 0.1 L/min or 0.01%: a refusal reaches the banner only when a slider and a limit disagree, which is most likely just past a limit, and the readout's rounding would then write the value equal to the limit it broke (10.04 L/min as "10.0 L/min" beside a highest flow of 10.0).

How. The four limits that a dial's setting can meet now raise `SettingOutsideRange`, a subclass of `SimulationConfigurationError` in `core/exceptions.py`: the flows' supported input range (`_require_supported`), the range of a percent (`Percent`), the vaporizer maximum (`require_within_vaporizer_maximum`) and the machine's flow range (`_require_deliverable_flow`). Each core message is unchanged and stays the developer's text. The error also carries the name of the field it refused, the value, both ends of the limit and which limit it was (`SettingLimit`) as fields. The constructor requires the fields, so the error rebuilds itself with them when it is copied or pickled (`__reduce__`), and a caller that rewords it keeps them (`reworded`, used by `_restored_blood_flow` in `core/blood_flow.py`). `core/` may not import `app/`, so it cannot name a control by its label, and building the learner's sentence from fields keeps the label in one place (`CONTROL_INPUT_LABELS`). `setting_refusal_for_a_learner` in `app/dashboard_frame.py` builds that sentence for the control that set the value, only when the refused field is that control's own, and keeps the core's message as the new error's note (`add_note`, PEP 678) and cause, as `PL-72X2` did for the branch refusals. `RunView._apply_setting` takes the control from each of the four dial handlers and logs the core's message at error level, so it reaches the failure log. A dial offers only values its run accepts, so a refusal that reaches the banner means the dial and the limit disagree, which is a fault worth a log line. A refusal the controller already words for the learner, such as a setting on a stopped run, is shown as it was, and so is a range refusal of another control's field, which the settings record can raise while it checks every field after one control moves. `CONTROL_INPUT_FIELDS` in `app/control_record.py` now names the field that holds each control's value, and `control_value` reads the field it names, so the name a refusal is matched against and the field a readout shows have one home.

Research behind the wording, read 2026-11-23: GOV.UK Design System, "Error message" (https://design-system.service.gov.uk/components/error-message): "Error messages should directly include language from the question or fieldset label", "Describe what has happened and tell them how to fix it", and its example states the limit ("35 characters or less"). Nielsen Norman Group, "Error-Message Guidelines" (Neusesser and Sunwall, 2023, https://www.nngroup.com/articles/error-message-guidelines/): "Avoid technical jargon and use language familiar to your users instead", and show error codes "for technical diagnostic purposes only". Microsoft Learn, "Error Message Guidelines" (https://learn.microsoft.com/en-us/windows/win32/debug/error-message-guidelines, updated 2025-07-14): "If a message has multiple audiences, you may need to provide separate text for administrators, end users, and developers", and a critical error is written to the event log. Google for Developers, "Write for the target audience" (https://developers.google.com/tech-writing/error-messages/target-audience, updated 2025-03-31): use the target audience's terminology. Each page was read through a fetch that returned the page's text.

Tests. `tests/unit/test_setting_refusal_wording.py` checks each limit's fields with values typed from `docs/INTERFACE.md` § "Supported input ranges", checks that a copy and a pickle keep them, and pins the learner's sentence, the note and the cause for each limit, including a flow and a dial just past their limits and an `int` too large for a `float`. `test_a_range_refusal_of_another_control_s_field_is_shown_as_it_is` checks that a vaporizer refusal met while cardiac output moves is not reworded. `test_a_refused_setting_is_reported_without_stopping_the_run` and `test_every_slider_handler_refuses_without_escaping_into_the_toolkit` in `tests/integration/simulation_view/test_simulation_view_refusals.py` now pin the whole banner for each of the five refusals they drive, and the first checks the error-level log record. Run against `origin/main` at `489d0992` with only that file copied in, five of its twelve tests fail; the vaporizer case's assertion shows the banner "Setting refused — delivered_concentration_percent exceeds the vaporizer maximum (50% requested, 5% maximum). The simulation is unchanged and still running its previous setting." The approved-wording list holds the new banner.

Documents checked: `docs/INTERFACE.md` (the supported-range refusal paragraph now says what the banner names, and its note for developers names the exception, the function and the tests), the module docstring of `core/validation.py` (it said the banner shows a refusal verbatim), and the docstrings of `test_a_refused_dial_setting_is_pinned_whole` and `test_a_setting_s_range_refusal_is_pinned_whole`, which said the core's sentence is what the banner shows. `docs/MODEL.md`, `docs/VERIFICATION.md` and `README.md` say nothing about the banner's wording.

**Generator check.** This is the last member of the generator that `PL-CCVP`'s brief records: a message written for a developer in `core/` or the controller reaches a panel verbatim. The branch refusals (`PL-72X2`) and this banner now both give the learner a sentence of their own and keep the developer's text as the error's note and in the failure log. Looking for more members found one: three MAC target refusals in `app/bookmarks.py` name a compartment by its code value, and the mark editor shows them verbatim. They are filed as `PL-5867`, because they need a compartment label read from its one home, which this change does not touch.
