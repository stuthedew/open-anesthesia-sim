**Problem.** Write user stories for the interface pass with the owner, each a need with a check that shows it is met, before the heuristic evaluation

**Where this comes from.** Lesson 44 of the owner's machine-control dashboard
project, adopted on 2026-11-27 (`PL-HWZK` has the sources). It becomes the new
first step of the interface pass's order of work, ahead of the heuristic
evaluation (`PL-8Q1P`).

**What to do.**

1. Draft user stories from what the simulator does and from
   `docs/consultant-brief.md`. Use the form "As a [type of user], I
   [need/want/am required] to [do something], so that [reason or benefit]"
   (Mountain Goat Software). State each need without naming a control, a View
   or a feature (Gibbons, NN/g, 2019). The user is an anesthesia clinician
   using general-purpose simulation software, not a learner.
2. Take the drafts to an interview with the owner, with the current build or a
   prototype in front of him, and have him correct and add to them (owner's
   rule, 2026-11-27).
3. Give each corrected story one check that shows the need is met, written so
   it can be tried in the mock-up walk-through and the resident rounds
   ("Confirmation", Jeffries 2001).
4. Replace `PL-8Q1P`'s four tasks with tasks drawn from those checks, and say
   in `PL-8Q1P` which story each task comes from.

**Why it matters.** The four tasks agreed on 2026-11-10 were written for "a
resident early in training who works through a case alone", and two of them
read as lesson steps rather than needs. The owner retired the learner framing
on 2026-11-27. A layout drawn for the wrong need is redone however well it is
styled.

**Done when.** This item records the stories as the owner corrected them, each
with its check, and `PL-8Q1P` lists its tasks against those stories.

**Generator check.** One-off: a new step the owner approved on 2026-11-27, not a fault with a cause.
