**Problem.** Three app/ surfaces own state a layout could duplicate or relocate beside PL-VN6M's TraceLegend: RunView's build_ accessors hand out the same widget object on every call, the chart time base is owned by a dropdown inside one plot's panel, and the chart's column budget is read from sibling plots

**Problem.** `SimulationView._refresh_view` assembles exactly one `ChartFrame` for the whole dashboard and samples it at `plot_width_px=max(self._concentration_chart.plot_width_px(), self._wash_in_chart.plot_width_px())` (`src/anesthesia_sim/app/simulation_view.py:451-453`). Both `ConcentrationChart.plot_width_px` (`src/anesthesia_sim/app/qt_chart.py:693`) and `WashInChart.plot_width_px` (`src/anesthesia_sim/app/qt_chart.py:1000`) carry the same docstring instruction — "Hand `chart_frame` the wider of this and the other plot's" — and `assemble_chart_frame` documents the parameter as "the wider of the two where both plots draw it" (`src/anesthesia_sim/app/chart_frame.py:696-700`). The column count that width produces *is* the drawn data's resolution (`chart_columns`, `src/anesthesia_sim/app/chart_frame.py:448`). The only thing that notices a width change is `SimulationView.resizeEvent` (`src/anesthesia_sim/app/simulation_view.py:496-507`), which sets `_render_pending`; nothing else in the module sets it except `present(coalesce=True)` and a run's `presentation_requested`.

**Why it matters.** `resizeEvent`'s own docstring states the failure it is there to prevent: "after a resize while paused, with nothing running and nothing owed, the columns drawn for the old width would stand on the new one at a chord wider than a pixel (`PL-GS3R`, `PL-25KS`)" — the drawn-chart accuracy item, whose worst error was 0.26 MAC across the steep early wash-in. That guard is attached to *the dashboard's* rectangle. An area border drag resizes a child widget and leaves `SimulationView`'s own geometry untouched, so it fires no `resizeEvent` and owes no frame; while paused, the widened plot keeps drawing the frame sampled for its old width. `inert_splitter` (`src/anesthesia_sim/app/qt_widgets.py:784`) is why this cannot happen today and why item 34 is exactly when it can. The `max()` over two named siblings is the second half: once each chart is an Editor in its own Area, the two have independent widths, either may be absent from a workspace, and two of the same kind may be open at different widths, so there is no longer "the other plot" to take a maximum with.

**Where.** `src/anesthesia_sim/app/simulation_view.py:429-453` (frame assembly), `:496-507` (the resize guard); `src/anesthesia_sim/app/chart_frame.py:676-742` (`assemble_chart_frame`, `plot_width_px`); `src/anesthesia_sim/app/qt_chart.py:693-700`, `:1000-1007`.

**Shape.** The contract the area model implies and nobody has written: a view is told the rectangle it draws into and asks for its own resample when that rectangle changes, rather than a container sampling one frame for a pair of plots it names by attribute. `PL-VN6M` (TraceLegend owns compartment visibility inside a widget) moves the *selection* out of a widget; this moves the *sampling width* out of the container and into the thing that owns the rectangle. `PL-PGZF` (assemble_chart_frame costs 15.4 ms at 1601 columns) is the cost side of the same parameter and should be read alongside it, since per-area sampling means assembling more than one frame per tick.

**Done when.** A view's drawn resolution follows its own rectangle rather than a maximum over two named siblings; a resize that changes one area's width and not the window's provokes a redraw of that area at its new width; and a test resizes a single chart while paused and asserts the redrawn series is sampled for the new width, which is the assertion that cannot be written while one frame serves both plots.

*Basis (lens `state-ownership`).* `.claude/rules/ui-areas.md` § "What it asks of a view you write today", test 4: "**A view does not assume its size.** An area border is a drag away from any width. Fixed geometry is for a swatch whose size is the point (`_LineSwatch`), never for a layout." The decided model adds that the area owns the rectangle and the view owns none, and `src/anesthesia_sim/app/qt_widgets.py:784` records that the handles are inert today "so that a later item can let a reader resize them by enabling the handles" — item 34 is that item.

**Problem.** `RunView` is a `QWidget` (`src/anesthesia_sim/app/run_view.py:231`) that is never placed in a layout: `SimulationView` builds one per controller (`src/anesthesia_sim/app/simulation_view.py:181`) and then distributes its parts across nine separate places in the page through nine `build_*` methods. Four of them return a widget the instance already owns — `build_header_badge` returns `self._agent_header_badge` (`:915`), `build_notice` returns `self._notice_text` (`:961`), `build_off_scale_notice` returns `self._off_scale_text` (`:1046`), `build_wash_in_state` returns `self._wash_in_state_text` (`:1051`). The other five build a fresh container and fill it with widgets the instance owns: `build_transport_row` (`:920`) adds `self._run_name_text`, `self._agent_dropdown`, `self._running_agent_display`, the three transport buttons and `self._status_text`; `build_readout_section` (`:966`) adds `self._compartment_substance_text`, `self._interpretation_text` and `self._readout_row`; `build_parameter_controls` (`:990`), `build_sidebar_panels` (`:1003`) and the rest do the same. `QLayout.addWidget` reparents, so calling any of these twice removes the widgets from wherever they were placed first — no error, no warning, the first placement simply empties. The class docstring records the design as intended: "The build methods return widgets for `SimulationView` to place, because where a run's parts sit relative to another run's is the dashboard's decision" (`:237-239`).

**Why it matters.** Under `ROADMAP.md` planned-milestone item 34 an Area holds one Editor and any editor can occupy any area, so the reader may open two areas on the same thing. There is no per-run view to open twice: the object exists but its nine renderers are singletons handed out by reference, and a second request for a run's readout section would take the readouts out of the first area rather than draw a second copy. `docs/MODEL.md` § "Minimum displayed outputs" → "What this list requires once the layout is the reader's" puts the six compartment concentrations and the delivered concentration in the unconditional set — "the values that no workspace may remove and nothing may cover" — and `build_readout_section` is the only thing that renders them. A silent reparent of `self._readout_row` is a required value leaving the display while the application still believes it is showing it, which is the exact failure that section states the occlusion rule against.

**Why this is not `PL-TH35`.** `PL-TH35` (define the common Editor contract every app/ view implements) writes what an editor must implement, and notes that "the readouts are not on it yet" for the given-what-it-draws half. It does not settle the prior question this item raises: a run's display state and its nine renderers are one object, so there is no candidate to *be* an editor and no way to instantiate one twice. The contract cannot be validated against a run until that is separated.

**Where.** `src/anesthesia_sim/app/run_view.py:231-252` (the class and its docstring), `:915-1054` (the nine `build_*` methods), and the per-run display state they render from — `self._rejected_setting_notice` (`:272`), `self._playback_rate` (`:273`), `self._pending_agent_id` (`:279`), `self._frame` (`:284`), `self._run_index` (`:285`); `src/anesthesia_sim/app/simulation_view.py:181`, `:241-243`, `:277-297` (the nine placements).

**Done when.** A run's display state is held somewhere a renderer is handed it rather than owning it, each run surface that will occupy an area can be constructed more than once against the same run, and a test builds two of one run's surfaces and asserts both draw — which is what cannot be written while `build_*` hands out the instance's own widgets.

*Basis (lens `state-ownership`).* `.claude/rules/ui-areas.md` § "What it asks of a view you write today", test 3: "**A view is instantiable more than once and assumes it is not alone.** `RunView` already is." That is true of the class and false of everything it hands out. Test 5 in the same file: "**A required value never moves into something closeable.** ... the unconditional set sits outside the area system. A value on that list does not go in an area."

**Problem.** `SimulationView._time_base` (`src/anesthesia_sim/app/simulation_view.py:182`) is not the source of truth for the time base; `self._time_base_dropdown` is. `_handle_time_base_change` reads the reader's choice back out of the widget — `key = self._time_base_dropdown.itemData(index)` — and derives `_time_base` from it (`:483-489`), so the combo box *is* the state, the same shape `TraceLegend`'s docstring records for compartment visibility. That dropdown is built into the concentration chart's own panel: `_build_chart_column` adds it to the chart heading row at `:348`, alongside `self._time_axis_caption` (`:349`), which is the rendered statement of the width in force. But the value governs both plots — one `ChartFrame` is assembled from it (`:449`) and drawn by `self._concentration_chart.draw(frame)` and `self._wash_in_chart.draw(frame)` (`:455-456`).

**Why it matters.** Under `ROADMAP.md` planned-milestone item 34 the concentration chart and the F_A/F_I plot become separate Editors in separate Areas, either of which a reader can close or open twice. Close the concentration chart and the wash-in plot keeps a time axis whose only control and whose only statement of width went with the other area — the identical failure `PL-VN6M` names for the legend and the compartment selection, for a different piece of state. Open two concentration-chart areas and there is no answer to which dropdown sets the width both are drawn at. `docs/MODEL.md` § "Minimum displayed outputs" already treats the time base as a display obligation rather than a convenience: "The time base is the one chart entry above that the reader does choose, and what this list requires of it is that the width in force is stated, never that any particular width is in force" — and the thing that states it is a label inside one of the two surfaces.

**Not the same item as `PL-VN6M`.** That item moves the compartment selection out of `TraceLegend` and names `qt_chart.py` and `simulation_view.py`'s `_handle_trace_visibility_change` in its `touches`. The time base is a different value, a different widget, a different handler and a different pair of readers, and its `Fit run` sentinel (`FIT_RUN_KEY`, `src/anesthesia_sim/app/chart_time_base.py:73`) is a shape the selection does not have. The fix is the same *pattern* — the dashboard owns the value and hands it down, the widget renders it and requests a change — which is a reason to file it, not a reason to fold it in.

**Where.** `src/anesthesia_sim/app/simulation_view.py:182` (`_time_base`), `:191-199` (the dropdown and its items), `:233` (the connection), `:348-349` (its placement inside the chart panel, with the caption), `:449` and `:455-456` (both plots drawn from it), `:483-489` (`_handle_time_base_change`).

**Done when.** The chosen time base is owned outside the widget that offers it, the dropdown renders it and requests changes to it, the statement of the width in force is available to each surface drawn at that width rather than only to the one holding the control, and a test asserts the chosen width survives the control being destroyed.

*Basis (lens `state-ownership`).* `.claude/rules/ui-areas.md` § "What it asks of a view you write today", test 2: "**State a layout could duplicate or relocate does not live inside the widget.** Ask who owns it when two areas show the same editor, or when the editor is closed and reopened. `TraceLegend` owning compartment visibility is the standing counter-example (`PL-VN6M`); a view holds its own scroll position, not the selection the rest of the dashboard draws from."
