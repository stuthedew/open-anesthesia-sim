**Problem.** The copy editor drops requirements, qualifiers and reasons that no number or code-span check sees: on docs/MODEL.md it weakened or lost about 120 statements in 42 of 78 edited sections, turning 'must' into descriptions and cutting 'only', 'no others' and stated reasons

**What happened.** `PL-95SW` line-edited `docs/MODEL.md` with the copy editor after its fix (`PL-HGZS`). The edit passed every check on numbers, equations, code names, citations, markers and dates. Two blind reviews then found 8 lost statements, and a full comparison of each edited section's old and new text by six review agents found about 120 more in 42 of 78 sections. The losses were of four kinds: a requirement turned into a description ("must lengthen" became "a test checks that ... lengthens"; "No scientific parameter may be added without" became "Every scientific parameter added comes with"); a limiting word cut ("only", "no others", "explicit", "tagged"); a stated reason cut (why a source is tier 2, why a tier-2 citation is legitimate); and a list item or scope clause dropped (the fourth exclusion from the reproducibility guarantee). Fourteen sections went back to their old wording and 34 statements were restored (`#2049`).

**Why it matters.** `docs/MODEL.md` is the safety-critical specification. A requirement restated as a description, or a limit that loses "only", reads as a weaker claim to a later session that cites it to decide what the code must do. The same tool edited `docs/machine-abstraction.md` and `docs/machine-survey.md` (`PL-B7V7`), and rule 16 runs it on replies.

**Open question for the fix.** Should the copy editor's instructions (`.claude/agents/copy-editor.md`) forbid these four kinds of change, or should `tools/copy_edit.py` add a comparison read like the one that found them? The project owner debugs the copy editor one section at a time and approves each (2026-11-04), so the change is the project owner's to direct.

**Approach** (chosen by this session on 2026-11-07 and told to the project owner in the thread, not yet ratified). The approach does both. The instructions are fixed where they invite the losses: step 4 lists "a reason the reader cannot act on" among what a reader can do without, step 3 rewrites a paragraph from a list of facts that carries no requirement's force, and the list of what must never be cut names no "must", no limiting word such as "only", no list count, no scope clause and no stated reason. `tools/copy_edit.py` also gains a comparison read after the edit, the meaning check. It is a separate run whose one job is to compare each original sentence with the edit for those five things, and each statement it finds lost goes back to the copy editor to be restored. The instructions already asked for that comparison twice (step 7, and step 3 of the second read), and up to four reads still lost about 120 statements, while an audit given that one job found them. Models broaden claims even when told to be accurate: "Even when explicitly prompted for accuracy, most LLMs produced broader generalizations" (Peters and Chin-Yee, arXiv:2504.00025, 2025). A model that reviews its own output without outside feedback rarely improves it (Huang et al., "Large Language Models Cannot Self-Correct Reasoning Yet", ICLR 2024, arXiv:2310.01798).

**Two checks a round** (this session, 2026-11-07). Part 75's first edit lost four statements: the scope of "the shipped tail", the reason a time bookmark past 24 hours cannot be made, the scope of "past roughly ten MAC-hours", and that the controller, not the interface, reports the limit. Runs of the meaning check on that edit found only one or two of them each, and later checks found the rest one at a time. With the limit then at three checks, the third check's finding never got a restore read, so the whole part was kept unedited (commit 3264d836 raised the limit). A test version of the check that wrote one line for each original sentence visited all 196 sentences and still marked three of the four kept. So the misses are judgments that vary from run to run, not sentences skipped, and asking the check to write a line for every sentence does not fix them. Each round now runs the check twice and restores what either run finds (commit 65b009c5). On part 42 the second check found a loss that run 3's checks and fresh audit had both passed: the note for developers no longer said that the three agents share the patient file.

**Test set.** The set is six parts of `docs/MODEL.md` as it stood before `#2049` (commit d26e8c70), as `tools/new_prose.py` splits it for a line edit. They are listed in the order they are reviewed, shortest first, with the losses the audit found in each: 42 "v0.2.0: isoflurane and desflurane" (5 losses, 1,187 words), 43 "Delivery-limit and MAC parameters" (6, 1,458), 75 "Supported run length" (10, 2,990), 37 "Supported simulation step" (5, 3,442), 118, the second run of "Known limitations" (7, 4,544), and 71 "The canonical evaluation rule" (13, 5,665). Until 2026-11-08, every change to the instructions sent the first part back for review, so a short first part kept that repeated review short. The audit findings are in the project's shared folder, `v0.7.0/repo-copy-edit/audit-findings/`.

**Done when.** On each part of the test set, the fixed copy editor keeps every statement that the audit found lost there, and a fresh audit of its edit by the same brief reports no requirement, limiting word, list item, scope clause or stated reason lost. The parts are approved one at a time, each before the next, and any change to the instructions starts again from the first (project owner, 2026-11-04). The owner approved parts 42 and 43 himself. From part 75 on, a part or any rerun of an earlier one is approved when it keeps every statement the audit found lost there, both checks in its last round find nothing lost, and the session's own sentence-by-sentence review finds nothing lost or unclear. The owner then gets one short summary at the end, which quotes any sentence that needs a clinician's call (project owner, 2026-11-08, ratified, over approving each part himself and over shorter requests for each part). He was tiring of the reviews, and they had caught unclear wording but no lost meaning, which the two checks now catch.

Since 2026-11-08 18:56 UTC, a change to the instructions no longer starts the parts again. The run goes on to the next part on the changed instructions, a part that failed is not rerun on its own, and once every part has run, each part that has not yet run on the final instructions runs once more on them, in an end pass (project owner, 2026-11-08). Part 75 failed on 2026-11-08 and the run went on to part 37. The end pass starts only once part 71 has been reviewed, so that no run is spent on instructions that part 71 could still change (project owner, 2026-11-08).

**Result on the test set.** The end pass ran on the final instructions (commit cd647afb) from 2026-11-08 22:33 UTC to 2026-11-09 00:10 UTC, and part 71 had already run on them. Part 42's edit kept all 5 statements that the audit had found lost there, part 43's all 6, part 118's all 7 and part 71's all 13, and a fresh audit of each edit found nothing else lost. Part 37's edit kept 4 of its 5. Its fifth, "No error is raised at any of these steps [...] and still returns normally", became "The model reports no fault at any of these steps [...] and the model still reports none". The edit keeps that the model gives no sign of the error, but no longer says that the step returns normally, which a developer needs. On part 75 the second check still found a loss in round 5: "Such an instant is the opening at which a branch's `RunDefinition` is built, or a point to which a run is moved" had become "such as the start of a branch or a point that a run is moved to", which turns a complete list of two into examples. So `tools/copy_edit.py` refused the edit and kept the original. The runs led to two rule changes: a general word is not swapped for a narrower term used nearby (commit 14c61164), and a moved sentence keeps what its pointing words point at (commit cd647afb). The end pass also found that a renamed bold lead can break a citation that the doc check cannot see (`PL-97S1`).

**Generator check.** The fact misread is that a passage the copy editor rewrote still says everything the original said, with the same force and scope. `PL-B7V7`, the audit of the two machine documents, is the only other item it caused, and a generator needs two. `PL-HGZS`'s misread is a different fact: that a passage the copy editor passed is plain enough for its reader. So this is a defect the owner asked to have fixed, and no generator.

**Decision.** The remaining copy edits of the repository wait until this is fixed (project owner, 2026-11-07, ratified, over continuing with a six-reviewer audit of each document before it merges). The edits of the references and the maintainer guide that ran on the owner's Mac (branch `claude/repo-copy-edit-api`) stay unmerged until then, and are re-run or audited on the fixed copy editor.

**The copy edits resume on this result** (project owner, 2026-11-09, ratified, over one more rule fix and a rerun of part 37 first). `PL-6BW8` records part 37's one less precise statement, which is fixed where `docs/MODEL.md` is line edited. Part 75 got no edit, so its section is line edited like any other when `docs/MODEL.md` is.
