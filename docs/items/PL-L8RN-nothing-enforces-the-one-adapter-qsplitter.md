**Problem.** Nothing enforces the one-adapter QSplitter confinement PL-C842 decided, because import_boundary_check.py confines root packages and PySide6 is one root package

**Problem.** Two decided properties of the area system are claims about imports and nothing measures either: `QSplitter` is confined to one adapter module (`ROADMAP.md` item 34, `PL-C842`), and the layout layer knows no concrete view type (`docs/interface-provenance.md`, "A view kind is a tag plus a registry lookup, never a subclass"). `PL-C842`'s closing argument records the first as already enforceable — "the same tool can enforce it" — and `tools/import_boundary_check.py` cannot, at either granularity. `module_imports()` keeps `alias.name.split(".")[0]` for `import X` and `node.module.split(".")[0]` for `from X import ...`, discarding the imported names entirely (its `ImportFrom` statement string is literally `f"from {node.module} import ..."`). So `from PySide6.QtWidgets import QSplitter` — the form in `src/anesthesia_sim/app/qt_widgets.py` — arrives as the root `PySide6`, indistinguishable from `QWidget`; `tests/unit/test_import_boundary_check.py::TestModuleImports::test_reaches_the_package` pins that granularity with `("from pydantic.fields import Field", "pydantic")`. A boundary confining `PySide6` to the adapter would therefore fail on every widget module in `app/`. The intra-package half is worse: `from anesthesia_sim.app.run_view import ...` has the root `anesthesia_sim`, so "the layout tree imports no view module" is not expressible at all.

**Why it matters.** These two imports are what interchangeability rests on. A view that can see a splitter is bound to one layout; a layout module that imports a view kind makes the registry decorative, and the tag-plus-lookup design reads as intact while the coupling is direct. Neither failure shows on screen, and every existing gate stays green — the shape `CLAUDE.md` names as belonging in a script rather than in prose nobody re-measures, and the shape this tool's own docstring was written against ("the docstring and the guarantee asserting the property would go on asserting it, reading as verified when it is not"). `PL-9KDK` is the precedent for the timing: the `PySide6`, `pyqtgraph` and `numpy` boundaries were declared before any of them existed in the tree, so the port's first commit was measured against the rule rather than the rule written around wherever the port had put things. The adapter has the same one-chance shape, and today's allowance would name `qt_widgets.py` — an 852-line general widget module holding `inert_splitter()` at line 784 — which is precisely the move the entry forces into the open when the adapter arrives.

**Done when.** `tools/import_boundary_check.py` decides a dotted import target — a `Boundary.package` containing a dot matched against `module + "." + alias.name` for `ImportFrom` and against the dotted name for `Import`, with relative and intra-package forms resolved so an `anesthesia_sim.app....` target can be confined — with the undecidable residue (attribute access through a bound module object, a computed name) stated as a limit in the same register as `test_a_computed_dynamic_name_is_a_stated_limit`. Two entries are declared with their reasons beside them, in the commit that creates the adapter rather than after it: `PySide6.QtWidgets.QSplitter` confined to the one adapter module, and the concrete view modules confined out of the layout tree. A boundary over a tree that does not exist yet is an `empty` error by construction, so the entries land with the directory rather than ahead of it — and the item records that, so the next session does not read the absence as an oversight.

*Basis (lens `registry`).* ROADMAP.md item 34: "A pure-Python `LayoutModel` is the source of truth ... with one adapter module the only place importing `QSplitter`. A view is registered by kind, never sees a splitter, never calls `saveState()`, and never stores its own geometry." (ROADMAP.md, item 34). docs/interface-provenance.md, § "Adopted": "**A view kind is a tag plus a registry lookup, never a subclass.** Nothing in the layout layer knows a concrete view type exists." PL-C842 asserts the enforcement already exists: "`tools/import_boundary_check.py` already confines the UI toolkit by declared boundary with the reason written beside it ... This is the same rule one level further out, and the same tool can enforce it." (docs/items/PL-C842-decide-whether-the-layout-container-sits-behind.md).
