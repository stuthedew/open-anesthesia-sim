**Problem.** Rewire branches_in_flight, precedence and settled_branches onto claims.holdings

**Part of `PL-MB2W`'s design** (who holds an item is recorded as a claim; design round of 2026-09-24, in `PL-MB2W` under "Design round, 2026-09-24"). Read that section's spec before starting: this brief names only this item's slice of it.

`branches_in_flight` becomes `holdings().flight()`, keeping `FlightReport`'s shape so its callers stay unchanged; `precedence` becomes `Holdings.order`, and its 19 tests are rewritten against it; `settled_branches` reads released holds. `flight` gains kind and state columns, an `unclaimed:` row per work branch that holds no claim, and a `legacy refs: N` line, and lists lapsed claims only for open items.

**Why it matters.** `PL-MB2W` is a live generator: twenty items were each a new shape of work that some reader misread, because who holds an item is inferred from commit subjects, touched paths and ref age. This item is one slice of replacing that inference with a recorded claim, and the generator stops producing members only once the slices through `PL-DDYD` land.

**Done when.**

- `branches_in_flight`, `precedence` and `settled_branches` answer from `claims.holdings`, and the digest, `next`, `flight` and `show` print the same fields as before plus kind and state.
- A ref named for its item holds that item where no claim or disposition does, including a ref whose history went unread (`PL-TZ3R`, folded in below).

**Build order.** After `PL-NST2`.

**The fault, reproduced 2026-09-24 on `b1d1b665`.** `cli.py`'s `_flight` still calls `vcs.branches_in_flight`, `cmd_show` still renders `vcs.precedence`, and `cmd_flight`'s settled row still calls `settled_branches` over that report. `claims.holdings` has no caller outside `claiming.py`, and `render.py` prints neither `legacy refs:` nor `unclaimed:`.

**`Holdings.flight()` reads no branch-name id, and this item carries it** (decided 2026-09-24 at triage, folding `PL-TZ3R` in). `branches_in_flight` proves an id from a name like `claude/pl-k7qx-slug`, even for a ref whose history went unread. The spec lists that reading under "Other holds", and this rewire is the change that would lose it. So `claims.holdings` gains it as a fourth kind of hold, beside dispositions and cuts. It never orders against a claim, never holds arming, runs on the branch's lease, and reaches `flight()` only where no claim or disposition holds the item. A ref whose history went unread still proves its id this way, as it does today, and stays in `unreadable` as well. Building it was chosen over dropping it because dropping it departs from the ratified spec, and it is cheap. For now it is also rare: 0 of the 8 non-default remote heads carried a name id on 2026-09-24.

**Leads for the rewire, read from the code on 2026-09-24 and not yet tested:**

- `flight()` drops released holds. A branch that closes its item in its own copy releases its claim (`BY_STATUS`), but it keeps the item in flight through the disposition that the same status move creates. So `settled_branches` probably wants the `Holdings` rather than the `FlightReport`: a ref is settled where it holds no live claim and every live hold it has is a disposition to a status in `CLOSED_STATUSES`. That uses `CLOSED_STATUSES`, not `RELEASING_STATUSES`, because a blocked item is not finished work.
- `test_cli.py` builds real git repositories (none of it fakes `for-each-ref`). No commit tree there holds `CUTOVER_MARKER`, so `holdings` reads every such commit by the legacy rule: subject-led ids on a commit that reaches outside the queue still claim, and the three promotions (`PL-7790`, `PL-VYSP`, `PL-8FJK`) do not. Expect the promotion tests to move, and nothing else by that route.
- `holdings` refuses a naive `now`, so `_flight` passes `_now(args)`.

       Scenario: Setup: a shallow clone where main is cut unevenly (main has merge commits; this repo has 117). Session S claims PL-K7QX on claude/some-slug with a `Claim:` trailer at 05:00. At 10:30 it merges origin/main, whose tip is then 'Main work 3' (authored 06:00). At 13:00 it commits 'PL-K7QX: the work'. Main then gains enough commits that 'Main work 3' falls below the clone's cut on the long path, while a shorter path still reaches the root. `git log ^origin/main origin/claude/some-slug` now lists main's own 'Main work 1', 'Main work 2' and 'Main work 3', every one with a parent, so `_history` does not mark the ref unread. In author-date order, 'Main work 3' comes after the claim commit, because it is reached through the merge's second parent and is not an ancestor of the claim. `_landed_through` walks back from the newest commit. It skips S's work commit, which writes a new blob. It accepts 'Main work 3': every blob it adds is on the base, and `_landing_split('Main work 3', fork)` is all on the base. So the prefix sits after the claim, and the claim is released as `landed`. Choices made inside the approach, most from a four-lens review whose eight confirmed findings are fixed here with regression tests:
   - *One claim commit is one claim.* A legacy claim counts for every branch reaching its commit, so a branch that merged another's tied with it, and each clone read its own branch first. `holdings` now breaks the tie on the branch name, and `show` groups holds by commit, printing one claim and no verdict, as `vcs.precedence` did.
   - *This branch means `HEAD`'s branch as well as this session.* A token decides `Hold.mine`, so another session's claim on the branch being read from was worded as another branch's. `Holdings.head` names `HEAD`'s ref, and that case is worded as another session's claim on this branch, matching `claim`, which answers by branch.
   - *A branch that recorded a claim does not also hold by its name* (`claims.holdings`, so `flight()` agrees). Otherwise a yield, a takeover or a close-out left the name holding for a lease more, worded as a branch that "records no claim".
   - *A lapsed claim prints only where no claim is live, and as free.* It holds nothing and `claim` passes it without `--over`, so `show` says `bin/docket claim <ID>` takes the item and offers `--over` for the record it adds. The `get_session`/owner gate is `claim`'s refusal for a live claim, and the computed task that asked to reuse it here carried no owner authority; gating a free item on it would also inflate `PL-MB2W`'s lease-revisit count of `--over` takeovers.
4. **Done: `settled_branches` onto the `Holdings`.** `claims.settled_branches(root, read, opened=...)` reads the `Holdings` `cmd_flight` already cached; `vcs.settled_branches` and its fake-runner tests are gone, and `SettledReport`, `SettledBranch` and the `opened` callable are unchanged. It runs no `git show`, since `Hold.status` is the copy's status, and its only git call is `remote`, made only when the forge answered. Choices made inside the approach:
   - *Every claim the ref recorded is asked* (`_finished_claim`), whether or not it won its item's row. A claim is finished only where it is released, and by a status move only to a closed status, so a `blocked` claim with no disposition behind it (a capture the base never had, or a block the base already shows) and a lapsed claim on an open item both keep the branch live. An item the branch blocked and the base later closed still reads as blocked, because release reads the branch's copy first; that errs live.
   - *Live dispositions and name holds must show a closed status*, so a name hold counts where the branch recorded no claim: a capture closed on its own named branch settles. A released or lapsed one asks nothing. Cuts are left out.
   - *Only refs with a `flight()` row, and only their own rows' ids*, so a settled row replaces live ones and never lists an id another branch's claim shows as live.
