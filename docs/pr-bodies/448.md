## What this changes

`PL-20CQ` reports that `docket check` runs every open item's `verify:` command, so a `verify:` naming `docket check` recurses without bound. Checked against the tree, that is not what happens - and the unbounded path is a different one.

**`docket check` re-entry is bounded twice over.** `already_passing` replays the commands only under `--verify`, which `make check` does not pass and no recorded command passes; and a nested run is stopped by `LANDED_GUARD`, which landed with `PL-3CBS` itself. The item's worked example fails a quieter way instead: the nested run declines the landed question, the grep never matches, the leading `!` inverts that, and the command passes without ever observing the advisory it was written to test. Vacuous rather than explosive.

**`docket verify` re-entry is unbounded, and nothing guarded it.** `verify_item` shells out `item.verify` directly, so an item recording `verify: bin/docket verify PL-20CQ` runs itself once per level, each level taking a fresh 1800 s timeout rather than a share of one. What ends it is the process table. This also falsifies the item's claim that every other `bin/docket` subcommand is safe: exactly two execute a `verify:` field, and `verify` is the unguarded one.

So what ships here is the refusal that holds under either reading of the item:

- `reenters_verify` in `verify.py` matches the command as text, stripping quoted spans first so that reading the store - `grep -q 'docket verify' docs/items/` - is not mistaken for running it.
- `docket check` errors on such an item, naming it and the shapes to use instead.
- `verify_item` reports the re-entry as a failed check rather than recursing, for a store nobody has validated yet.
- `subprojects/docket/README.md` documents the constraint beside the rule that a command is run before it is written.

`bin/docket check && grep -q ...` is deliberately left alone. It is the paired shape the docket skill recommends and **ten open items record it**; erroring on it would have failed `make check` on the store the rule exists to protect.

## Not done here

The item's literal **Done when.** asks for an error on any `verify:` re-entering `docket check`. That must not be built as written, for the reason above. The narrower target is a command reading the nested run's *output* rather than its exit status, which is the only shape that can pass vacuously - recorded on the item as a **Decision needed.** with three answers and a recommendation, so `PL-20CQ` stays open at `needs-decision` rather than closing on half its brief.
