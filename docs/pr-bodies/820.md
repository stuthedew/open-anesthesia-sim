`bin/docket new` was the only writer of `recurrences:` and nothing read the other direction. A match made on title similarity a reader disagreed with was permanent: the field is deliberately outside `docket set` — "the field's whole worth is that each entry was written by the tool at the moment it matched a filing" (`PL-X5JR`) — so the only correction available was hand-editing another item's front matter, which is the thing that rule exists to prevent. A false entry inflates an item toward the generator tier, which ranks above every band but `P0`.

That argument is about *writing* an entry, and it does not carry across to withdrawing one. The hazard of a field nothing can write is a fabricated filing; the hazard of one nothing can withdraw is a false filing nobody can correct.

## The command

```
bin/docket withdraw ITEM CAPTURE --because BRIEF
```

**It annotates rather than deletes**, which is what makes the correction as auditable as the write it undoes:

```
recurrences: 2026-09-20 PL-S8JT withdrawn 2026-09-21 PL-34BG
```

The entry stays where it was, saying the match was made on that date and disowned on this one. Deleting it would leave a file reading as though `docket new` had never matched anything — a quieter record than the one that was there before, and the one event in this mechanism's life with no trace. `PL-34BG`'s own brief made the same point from the other side: the entry was left standing because it is "the only physical evidence of the mechanism's first miss".

`--because` names an item, not a sentence. Why a match was wrong is a judgment — the half this mechanism refuses to make — so it lives in a brief, and the field carries the pointer a reader opens.

## What reads the new form

- `live_recurrences` is what every count and display reads; `recurrences_of` still returns the raw field. `recurrence_count` drops withdrawn entries, so `plan.recurring`, the digest line and `docket next`'s promotion candidate go quiet without any of them changing.
- `duplicates.anchor` counts live entries. A disowned entry would otherwise keep pulling later captures onto the item a reader just said they do not belong on — the one way a single false match could compound into a cluster.
- `docket show` prints withdrawn matches under their own heading, outside the filings.
- `docket check` holds the withdrawal's pointer to a real item exactly as it holds the capture's id, and reports a tail it cannot read as `withdrawn DATE PL-XXXX` — which leaves the entry *counting*, so a mis-typed withdrawal fails loudly rather than cancelling a filing in silence.

## The close-out audit, on both sides

The write is exempt and the withdrawal is not. An append rides a capture `CLAUDE.md` requires unconditionally and its value is dictated rather than chosen; a withdrawal is deliberate, and what it changes is how much evidence an item carries. Two consequences in `verify.sanctioned_queue_edit`:

- `_recurrences_grew` now requires what the line gained to start a *new* entry rather than extend the last one. Withdrawing the final entry appends to that line exactly as a fresh filing does, so without this the rule written for the edit that adds evidence would have exempted the one edit that cancels it.
- `RECURRENCE_LINE_RE` admits the withdrawn form, so one withdrawal does not make every later capture matched to that item read as tampering.

`withdraw` says so where the withdrawing item has not declared the file it is about to change, and is silent where it has.
