## What this is

Asked how the balance of workflow work to product work had moved over time, a session had no command to run. Every `bin/docket` subcommand describes the project as it stands — `status` by feature, `wave` by the release cadence, `next` by what to do now — and none of them looks backwards. Answering meant importing `Item.lane`, bucketing all 650 items by `added` and `closed`, and cross-checking against `git log --numstat` classified by `workflow_paths`, by hand, at full context.

That is a pure function of the item store and the git history, so it belongs in code rather than being re-derived by every session that gets asked.

## Design notes

**Three measures side by side, never reduced to one**, because each is wrong in a way the others are not. Item counts overstate the apparatus by roughly half, since workflow items are systematically smaller (mean effort 1.22 against product's 1.83 on this store). Effort weighting corrects for that but leans on a size ladder — S=1, M=3, L=8 — that is a convention rather than a measurement, so the ladder is printed under the column that uses it. Churn is the only measure read from what actually changed rather than from what an item declared, so it is the one that still answers where `touches` is missing or wrong.

**`Item.lane` and `is_under` are reused verbatim**, not reimplemented, so the trend and `docket next product` cannot give different answers about where an item sits.

**`crossing` and `unplaced` keep their own columns** for the same reason `next` names them: neither is a side, and folding either in would be a verdict the data does not support.

**Churn splits finer than the lanes do**, because two categories would otherwise say the wrong thing. The queue store is inside `workflow_paths` and belongs there, but it is written by every session that captures a finding while doing something else — so it is reported and left out of the share. The roadmap is deliberately outside `workflow_paths` since product direction is product work, but a period spent rewriting it is not a period spent building anything, so it is separated from code by the new `code_paths` setting (default `src`, `tests`; this project needs no config change).

**Periods anchor at the first day the report has anything to say about**, never counted back from today, so two runs a day apart agree about what happened in August. An empty period is dropped rather than printed as a row of zeroes; a period where neither side moved shows a dash rather than `0%`, which would read as a period of pure product work.

**Like `wave`, it computes and decides nothing.** Whether the balance it prints is the right one is a judgment about the project. It is deliberately not wired into `make check` or the session-start digest: it answers a question asked occasionally, and a check that fires every run without changing a decision is a defect in the check.
