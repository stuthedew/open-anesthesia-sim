## The defect

The `pr` number does not exist until the pull request is open, so an item could not be closed in the same commit as the work it closes *and* carry it. The order was forced:

1. commit the work, item still `ready` (or `make check` fails);
2. push, open the pull request — which is what mints the number;
3. commit the closure carrying it, and push again.

Step 3 is a separate push arriving seconds to minutes after the PR opens. A merge inside that window takes the work and leaves the closure on the branch: `main` has the fix while the queue still calls the item open and a debt gate still counts it. On `PL-D2GW` the window was 100 seconds wide and that is exactly what happened — recovery cost a branch restart, a cherry-pick, and a second pull request for a one-file change.

What falls through is the *record*, not the code, which is why it goes unnoticed: the diff, `main` and CI all look correct.

## The route

Chosen by the project owner from the three the item recorded: **error only on `main`.** The other two moved the failure rather than closing it — filling `pr` in a later pass needs a pass someone remembers to run, and scripting the rescue only shortens it.

`vcs.ClosureReport` and `vcs.closures_on_base` read whether each closure in question already stands on the default base. `checks._check_closures` owes a `pr` only for those, and `cli`'s `check` command supplies it; the unconditional per-item error is gone. A closure that reads `done` only in the working tree is now the expected shape — which is what lets it travel in the same commit as its work, so the window never opens.

## It does not decline on a shallow clone

This is the point that makes it usable, and it is a deliberate difference from `merged_pull_requests`. That reader needs *history*, which a truncated clone answers confidently and wrongly, so it declines. This one needs a single tree read, and `git show <ref>:<path>` is correct however little history stands behind the ref.

An agent session normally runs in a shallow clone, so a reader that declined there would decline in exactly the case the rule exists to cover. It declines only when no default branch resolves at all — reported as not-checked rather than passing, per the precedent `PL-XCYB` set.
