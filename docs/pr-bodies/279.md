Closes `PL-MC8Z` — the start-an-item guard checks who is on the item but never what files it touches, so overlap is found at merge.

## The problem, reproduced on the way to picking the item

The `docket` skill's "Mode: start an item" is a three-step guard — `git fetch origin`, `bin/docket show <id>`, then the session-list scan — and all three answer *is another session on this item?* None asks *is another session in these files?*

While choosing between three apparatus items this session ran `bin/docket concurrent PL-20CQ`. It listed eleven items it could not run alongside and said nothing about `origin/claude/perf-investigation-xnlfed`, which had commits from that morning in `checks.py`, `verify.py` and `test_checks.py` — `PL-20CQ`'s entire file set. It was found by hand, with `git diff --name-only origin/main...<ref>` over every remote branch.

## What changed

The brief scopes a prose fix — one step in the guard telling a session to run `bin/docket concurrent <id>`. That is here, and so is a second half, approved by the project owner, because the prose half alone would not have caught the collision above: `concurrent` compares one item's `touches` against another's, and `touches` is a prediction the branch had wandered outside of.

- **`vcs.files_in_flight`** diffs each unmerged ref against the default branch (`base...ref`, so the default branch's own commits are not re-reported as the branch's work). Kept out of `branches_in_flight`, which is on the hot path of `next`, `list`, `triage`, `status` and the session digest — this costs a `git diff` per ref and is paid only by the callers that ask the file question.
- **`concurrency.observed_conflicts`** matches those files against the item's `touches` using the existing `_covers` logic, excludes the item's own branch, and reports the file the branch changed rather than the declaration that matched it.
- **`docket concurrent <id>`** prints them as their own section, kept separate from declared overlap: the two are different kinds of evidence and only one says the collision has already happened.

Against the case that produced the finding it now says:

```
  Already changed on a branch in flight (observed, not declared):
    origin/claude/perf-investigation-xnlfed (PL-8BFV, PL-9NKK, PL-D3M2, PL-FRGP, PL-X3WZ) has changed:
      subprojects/docket/src/docket/checks.py
      subprojects/docket/src/docket/verify.py
      subprojects/docket/tests/test_checks.py
```

## No false clean bills of health

The observed half inherits the in-flight read's refusals rather than routing around them:

- A ref whose commits `branches_in_flight` could not compare is not diffed either — the merge-base a three-dot diff needs is the one that already failed to resolve.
- `_run_git` answers a failure with the same empty string a clean branch gives, so an empty diff on a ref that *holds* commits the base does not is named as unread rather than reported as a branch that changed nothing.
- An empty section is worded as "no branch has touched these files *yet*", and says so about files the item touches without having declared them.
