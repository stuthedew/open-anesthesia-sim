## The defect

`branches_in_flight` split candidate refs on whether `git merge-base BASE REF` returned anything and treated the readable half as answerable. A resolvable merge-base proves the two share *a* commit this checkout can see; it says nothing about the walk below it.

`^base` excludes only what the checkout can reach *from* the default branch, and in a truncated clone the default branch's own history ends at a grafted commit — so everything below that graft goes unexcluded. A ref reaching round it (one merge of the default branch into a branch is enough) then has the default branch's own commits reported as its work, and the ids leading their subjects reported as items somebody is implementing.

On 2026-08-31 that put twenty-seven ids in a session's digest, under a line telling it not to start them again: eighteen were closed, and one of the nine open was `PL-NSN9`, an entry of the release that same session had just been asked to finish. The direction is the dangerous one — a false positive here removes an item from `docket next` rather than adding noise.

## The fix

The walk now has to stop against a commit the default branch accounted for, never because the checkout ran out of history. A commit with no parents in this checkout is the signature of the second — a grafted boundary, or a root the default branch should have excluded — so `%p` joins the commit format and a ref whose walk emits one is named as unread rather than believed.

That is the same disposition a ref with no readable merge-base already gets, and it costs no extra git invocation: the parent field rides the walk that was already being run. Reading the commits is what settles it rather than `--is-shallow-repository`, so a git too old to answer that is guarded too.

## The reproduction

`_shallow_pair` in `test_cli.py` builds it with real git rather than asserting it: the default branch is fetched to a depth that leaves it grafted, and the branch to a depth that carries it past the graft. That is the intermediate depth the incident hit, and the one a `--depth 1` clone does not reach — there the merge-base declines and the existing guard already covers it. The test asserts the merge-base resolves before asserting the report, so it cannot silently degrade into re-testing the covered case.

Both the injected-runner tests (`-k contained`) and the real-git test fail with the guard disabled and pass with it.
