Closes `PL-QDH7` (guard `tools/`'s standard-library-only promise), a v0.2.8 gate entry. Also captures `PL-768D` (the guard reads the running interpreter's stdlib, not the floor's), untriaged.

## What was unguarded

`tools/doc_check.py`'s module docstring promises "standard library only ... so this runs in a bare checkout exactly as it runs in CI", and `tools/ruff.toml` repeats it. Nothing held it to that.

`make check` ends with `python3 tools/doc_check.py check` under whatever interpreter is on PATH — no virtualenv, no install step. An import satisfied only by `uv sync` therefore turns that line into a `ModuleNotFoundError` in a file the whole suite has just passed, because the suite runs under the virtualenv where the import resolves. That is the import twin of the `SyntaxError` `PL-921W` pinned the formatter against, with the same blast radius and the same "fixed where it fired, left where it also applies" shape: `subprojects/docket/tests/test_portability.py` has guarded its own package with an `ALLOWED_IMPORTS` allowlist since it broke this way once.

## The guard

`tests/unit/test_tools_portability.py` already walks every file under `tools/` with `ast` for the parse check, so the import walk is the same traversal. Each absolute import's top-level name must be in `sys.stdlib_module_names` or in `VENDORED`, which holds `docket` alone — in-tree under `subprojects/docket/src`, itself standard-library-only, and reached by path insertion rather than by installation, so a fresh clone carries it.

`sys.stdlib_module_names` rather than a hand-written allowlist: the interpreter maintains it, so nothing here goes stale as the standard library grows. Relative imports are skipped, and the helper says why — `tools/` is flat scripts with no package around them, so one resolves to nothing and fails on the first run rather than only in a bare checkout, which is a different failure from the one this test exists to catch.

## The bound, and why it is an item rather than a fix

`sys.stdlib_module_names` answers for the interpreter running the test — the virtualenv, 3.14.7 in this container — not for the 3.11 floor `subprojects/docket/pyproject.toml` declares. A module added between the two is allowed here and absent where it matters; `annotationlib` and `compression` are the live examples, both in 3.14's set and neither in 3.11's. That direction fails open. The reverse (a module removed after the floor) fails safe and loud.

It is narrow — CPython added two top-level modules across 3.12–3.14, neither one a documentation checker would reach for — and no standard-library route derives the floor's set, so the choice between the three available workarounds is a real decision rather than an obvious fix. Named in the test docstring with both examples and captured as `PL-768D`, which carries the diagnosis and the three routes with none chosen.
