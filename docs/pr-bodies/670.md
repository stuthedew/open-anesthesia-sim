## 1. `tools/generator_check.py` — the self-generation ratio, computed

`CLAUDE.md`'s "friction that compounds is recommended the moment it is found" is prose, so it needs a session to notice. `P2` holds 187 items, and a cluster handing back an item for every one it closes sits there unranked — `PL-BHVM` (the nineteen-item `vcs.py` cluster) did, for days.

For a path `p` named in `touches`:

    r(p) = items spawned by work on p's closed items that ALSO declare p
           / p's closed items

Spawn attribution is the project's own method, already used by hand in `PL-6ZQY`: the commit that adds an item file leads its subject with the id of the item being worked.

**The same-cluster restriction is the design.** A session closing an item captures whatever else it noticed, and those captures attribute to the item it was working, so counting every spawned child rates any heavily-worked file a generator:

| path | r loose | r tight | closed | open |
| --- | --- | --- | --- | --- |
| `src/anesthesia_sim/core` | 5.08 | 0.17 | 12 | 2 |
| `docs/MODEL.md` | 2.51 | 0.55 | 154 | 40 |
| `subprojects/docket/src/docket/vcs.py` | 2.33 | 0.71 | 52 | 12 |

The loose column ranks how busy a file is. It is not a generator measure.

Two attribution bugs the tests caught, both inflating the ratio: a multi-title `bin/docket new` commit leads with every id it creates, so each captured item was recorded as the others' parent; and a `touches` entry written `docs/items/` escaped the store exclusion that `docs/items` matched.

`PL-BHVM`'s `r_vcs = 1.05` is corrected to **0.71** in that item. Its urgency framing is retracted there; its duplication argument is untouched.
