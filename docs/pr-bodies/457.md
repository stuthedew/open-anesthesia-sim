## What was wrong

`ROADMAP.md` states one unconditional rule twice — step 4 of "The cadence" and "The gate is a snapshot, not a moving target" — and `PL-9PMV` settled that the two passages are the same rule: an item classed `safety` or `science`, or one at `P0`, re-enters the **current** gate regardless of when it was found. Every other class turns on whether its problem predates the freeze, which is a judgment; this one does not.

Fifteen `safety`/`science` items were filed between the freeze and 2026-09-07. Four — `PL-1XPX`, `PL-CTD7`, `PL-W7H9`, `PL-Z3W6` — are placed in v0.5.0's `Required scope` and clear *with* the milestone. The other eleven appeared nowhere in `ROADMAP.md`.

Ten of the eleven are `P1`. `docket check` pins both classes to the top band, so the gate — the project's stated readiness measure for v0.5.0 — was showing a list of 84 open entries that were all `P2` and `P3`, with every open `P1` the project had omitted from it. Nothing was inconsistent in the file; the count was right about the document and wrong about the project.

## What this changes

**The eleven are recorded** (`109f685`) as a dated group beside the two the freeze day already carried, citing the rule they re-enter under, with the four excluded ones named and the reason given. The v0.5.0 timeline row's count moves with the list rather than recording the freeze-day figure, because `check_gate_counts` reads a table cell as a claim about the list as it stands; the freeze date and the additions' dates carry the history instead.

`bin/docket wave` now reports **132 entries, 37 cleared, 95 open**.

**`check_gate_reentries` reconciles the two from now on** (`867d5cc`). It names every open `safety`- or `science`-classed item the current gate's section does not place, on its frozen list or under `Required scope`. Run against the tree as it stood before the recording commit, it reproduces exactly the eleven.

An advisory rather than an error, because only half the question is decidable. Whether an item is *placed* is: `MilestoneSection.scope_ids` already names the ids a section places and excludes one it merely mentions, which is the distinction `PL-NBCS` records. What an unplaced item should *become* — the frozen list, `Required scope`, or a deferral with a recorded reason — is the judgment the gate rule explicitly grants, so the advisory names the three dispositions and chooses none.

The gate it reads is the first *unreleased* section recording one, the same selection `docket.roadmap` makes, so an open item is never measured against a shipped milestone's closed list. With no single current-baseline row it returns silently: `check_baseline` makes that condition a hard error, so the run cannot be green while it holds.

`doc_check` now borrows `docket.config`, `docket.model` and `docket.store` beside `docket.roadmap`. All four are standard-library only, so the bare-`python3` floor is unchanged and CI's pre-virtualenv floor run is unaffected.
