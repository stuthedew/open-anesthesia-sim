## PL-RC0M — a blocked item's `verify:` command is never replayed

Option 2, taken first because it is the silent-wrong-answer case: `docket
check` reports the store sound while holding a command that proves nothing.
`PL-N092`'s command was `doc_check check && ! grep -q '…' README.md`; when

success. It passed on a tree where none of the work had been done, for a day,
invisibly — and the pull request that unblocked the item is the one that then

`SCOPED_ONLY_STATUSES = ("blocked",)` joins the candidate statuses **only when
`scoped_to` is not `None`**. The whole-store sweep on `push` to `main` costs
exactly what it did; a `pull_request` run, already narrowed to `changed_items`
by `PL-SDHR`, asks about a blocked item the branch touched.

`checks.py` words it as one reading rather than two. The standing message
offers "either the work landed — close it — or the command does not
discriminate", and for work nobody can start the first branch is impossible,
so that sentence would send a session at a status edit when the command is
what is broken.
