Closes `PL-VM40` (simulated time from a step count), v0.4.0 Required scope.

## What changed

**`SimulationState` holds a step count, not a running total.** `elapsed_s` is now a read-only property returning `step_count * simulation_step_s` — one multiplication, rounded once, rather than a sum rounded at every step. Ten 0.1 s steps summed to `0.9999999999999999`; they are `1.0` exactly now. Over a four-hour run the two formulations differ by about 35 ns, so nothing displayed today can tell them apart. What the product buys is not accuracy but path-independence: the value is a function of how far the run has gone rather than of the order and number of the additions that reached it, which is what an element-wise comparison of one run against another needs.

**A run keeps the step it started at.** `advance()` records the step its first step was taken at and refuses a different one thereafter, as a `SimulationConfigurationError` raised before anything moves. The product needs one step to multiply by, and a history recorded at two cadences has a sample spacing that is not a constant of the run — which every reader that maps a sample index to a time assumes it is. `reset()` frees it, so a fresh run may take a different step. The cadence decision stays in `app/simulation_view.py`, where a comment derives 0.1 s from the operator split's applicability domain; fixing the step *per run* rather than hard-coding it also leaves a step-refinement study able to take a whole run at a smaller step.

**The run loop is unchanged and now says why.** One step per tick already is a fixed number of steps per tick; what was missing was the statement that no tick may take extra steps to make up lost wall-clock time, and a test holding it there. A `STEPS_PER_TICK` constant would have no consumer today — `PL-SN2C` (the playback multiplier, implemented as steps per tick and never as a larger step) is where one belongs.

## Tests

- `test_a_run_keeps_the_step_it_started_at`, plus construction-time guards for a negative, fractional or unaccompanied step count and for a step outside the applicability domain.
- `test_a_run_records_the_same_history_however_the_ticks_fell` — the same 600 steps and the same settings at the same step counts, taken one per tick and in ragged bursts with the interface reading the run between ticks at different rates, compared sample by sample rather than endpoint against endpoint. The existing required replay test drives both runs identically, so it holds the model to one trajectory twice and says nothing about the machine.
- `test_the_run_loop_takes_one_step_per_tick_and_never_catches_up` — driven through a tick that returns at once, so the assertion is "one step per wakeup" with no real time in it. Checked against a loop mutated to take two steps per tick, which it fails.
