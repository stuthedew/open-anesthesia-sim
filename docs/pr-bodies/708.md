## What was wrong

The store names an item file from its title, so re-rendering a file whose slug has drifted renames it. Two commands did that while writing a field they had been asked for:

- `bin/docket record` writing `pr:` — observed on `PL-XQRK`, and earlier on `PL-36R4` and `PL-DZFJ`.
- `bin/docket release` stamping `milestone:` — observed moving `PL-XQRK`'s file during the `v0.4.28` cut.

Seven of the 1,239 files in the store carry a drifted slug today, four of them `ready`, one of them the current top of the queue.

## Why it is worth more than a tidier filename

The rename turns one added line into a delete-plus-add.

The `docket` skill grants `record` a standing exemption from the in-flight guard every other item-editing path owes, on the grounds that two sessions running it write the same tool-dictated line and git merges them. A delete-plus-add defeats that: the second to merge takes a modify/delete conflict on a file nobody edited on purpose.

Backing the write out then made it worse. `git checkout -- docs/items/` restored the tracked deletion and left the untracked new name, so the store held two files for one id and `bin/docket check` errored with `used by more than one file`. A session following the skill's own instructions reached a broken store.

A release cut is the worse of the two callers: it stamps every finished item at once, into the commit a release tag points at, and it is the write least likely to be reviewed file by file.

## The fix

`store.rewrite_item` already existed for exactly this. `PL-L4YG` built it for `docket set` and its docstring names `PL-LBR6` as the reason — but only `set` was wired to it, which is why the defect outlived the item filed for it and was re-discovered twice.

- `_write_pr` and `cmd_release`'s stamp loop now call `rewrite_item`, which writes back to the file it read.
- `write_item`'s docstring says it is for creating an item and for a pass whose subject is the rename. Its `replace=` branch now has no caller (captured as `PL-9KSY`).
- `subprojects/docket/README.md` states the name-keeping rule for every field write rather than as `docket set`'s own property.

No decision was taken here that the project had not already taken. Whether to stop re-deriving the slug or to rename deliberately and stage both sides was settled in `rewrite_item`'s docstring against `PL-LBR6` and `PL-YTDN`; two callers were brought to it.

## Tests

- `test_a_cut_does_not_rename_the_files_it_stamps` — a real cut over `done.md`, the same shape.

`_interrupt_after`, which stops the stamp loop part way to stand for a lost container, was retargeted to the writer the loop now calls, so the interrupted-cut tests still interrupt it.

`PL-LBR6`'s `verify:` loses its `pytest` prerequisite clause, per the 2026-09-19 rule that the discriminating `grep` stands alone.
