Before: the suite's mutation testing had been run once, by hand, in a scratch setup that no longer exists. Nobody could run it again, compare a later run with it, or ask whether a pull request's own tests catch faults in the code it changes.

After: `make mutate` mutates the functions the branch changed and prints each survivor's diff, in about five minutes. `make mutate ARGS=--all` mutates the whole tree. `docs/mutation-testing.md` holds the recipe, how to sort a survivor, the second-tier run against the whole suite, the measured pitfalls and the 2026-10-17 audit baseline. Close-out gains step 7, which runs `make mutate` where a diff changes a mutated function. It measures and never gates, as the owner chose (`PL-Y1PS`).

How: `tools/diff_mutation.py` reads `[tool.mutmut]` in `pyproject.toml`, works out which functions changed between the fork from the default branch and the working tree, and passes their mutant names to mutmut 3.8.0, which is pinned in its own `mutation` dependency group so `uv sync` leaves it out. It writes the test selection itself: every unit test file that imports the simulator, by the import rule `docket.arming` already applies (43 files today, against the audit's hand-written 33). Each run starts from an empty `mutants/`, because mutmut keeps old verdicts when a test changes.

One finding corrects the audit. mutmut reports any exception in its worker as a timeout, with exit status 255. That happens when a mutant raises while a test module is imported, so pytest cannot collect the test. The tool reruns those mutants' test files whole, after a control run with no mutant, and reports what they say. In a trial, all 5 such "timeouts" were kills. The audit's advice to raise `timeout_constant` is not followed.
