## The defect

A shell pipeline reports the status of its **last** stage. `make check 2>&1 | tail -45` therefore exits with `tail`'s status, and `tail` succeeds on any input, so a red tree arrives at the session as exit 0.

The harness flags a non-zero exit and says nothing about an exit 0. So the pipe does not merely *hide* the verdict — it substitutes the opposite one, with no signal that a substitution happened.

`PL-2JRC` is what that cost: that session ran exactly this command, read exit 0, and reported the gate green in its commit message and in the body of `#880`. The tree it pushed was red. The correction is the block that body now opens with.

## The decision: a hook, not prose

`.claude/hooks/gate-status-guard.sh`, a `PreToolUse` deny on `Bash`, wired beside `no-prune-guard.sh` and `floor-interpreter-guard.sh`.

Prose could not have caught this, for two specific reasons rather than a general preference. The rule has to fire when a command is *written*, which no read precedes, so no path-scoped rule reaches it. And it has to fire inside exploration subagents, which carry none of the main session's resident context but do run these hooks. `permissionDecisionReason` is shown to the model, so the refusal arrives at the one moment the wrong conclusion would have formed. `no-prune-guard.sh` made the same move out of ten resident lines (`PL-JK0M`).

**Resident context is unchanged at 70,835 characters against `origin/main`** — `make check` reports it, and the rule lives in the hook and its refusal rather than in prose every session carries.

## Why the remedy is `set -o pipefail` and not "do not pipe"

This is the part that decides whether the guard survives contact. The session piped because a passing `make check` is thousands of tokens of output it is asked *not* to load. A guard answering "drop the pipe" would trade a false green for a blown context budget, and would be routed around within a week.

`set -o pipefail` makes a pipeline report its rightmost non-zero stage. Output stays just as short, a red gate still exits non-zero, it is one token, and it is never wrong to add. The deny message leads with it.

Three other spellings are accepted: `&&` (short-circuits on failure), the redirect-then-read form, and reading `$?` straight out into the output.

## Guarding `make check` alone was refused

That is the observed instance, not the fault. The fault is that a verification command's status can be discarded, and `uv run pytest -q 2>&1 | tail -20` — the shape a session runs most often while iterating — loses it one command down. The `Makefile`'s own `--no-cache` comment settles this shape of question the same way: a fix that "treats the instance rather than the fault" leaves the next spelling to find it again.

## The guard caught its own author, and that is the second commit

Its first live firing refused `make check > /tmp/gate.log 2>&1; echo "exit=$?"` on the `;` — right about the separator, wrong about the command, because that `echo` *is* the reader and puts the verdict in the output in words. `CLAUDE.md` retires a check that fires without changing a decision, so the exemption was the fix rather than a concession.

Reading `$?` is now accepted, restricted to the segment immediately after the separator (anything in between replaces `$?` with its own status) and never after `&`, where `$?` is the background launch rather than the gate. Both bounds are pinned by tests.
