## The wrong number `docket check` offered

For `PL-YLZQ` the advisory said:

```
PL-YLZQ: marked done on `origin/main` and records no `pr`, but #159 is
recoverable from its merge commit; write `pr: 159` into the item so the
file carries it too
```

`#159` is `fce85ff`, the commit that **triaged** `PL-YLZQ` into the queue. The correct number is `204`.

The recovery takes the newest commit on the default branch whose subject names the item's id. `PL-YLZQ` was closed as a rider on `PL-026`'s pull request, so the closing commit's subject leads with `PL-026` and never names `PL-YLZQ` — leaving the triage commit as the newest match. `PL-KQKM` shows the safe half of the same blind spot: no commit subject names it, so it drew no advisory rather than a wrong one.

Finding nothing would have been harmless. Naming a wrong number and instructing a session to write it in is not: `subprojects/docket/README.md` says a closed item's whole traceability is the pointer from it to the work, so obeying the advisory replaces absent provenance with **false** provenance aimed at a commit containing none of the work — and the number is real and resolvable, so a session has no cue it is wrong.

Rider closures are not an edge case here. `CLAUDE.md`'s capture rule and the `docket` skill both direct that a finding an in-progress item needs in order to be properly finished is worked with it, on one branch, closed together — which is exactly the shape that produces them.

Captured as `PL-GW37` (untriaged) with the observation, the reasoning, the blind-spot half, and one approach to weigh: require that the matching commit's diff actually set the item's `status: done`, and stay silent otherwise, the way it already does for `PL-KQKM`.
