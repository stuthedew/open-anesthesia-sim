## Summary

Closes `PL-2XTF` with both halves the project owner chose: recover the number after the fact, **and** refuse the title that loses it beforehand.

`#220` was created from the Claude Code UI with a title naming none of the three items it closed. A squash merge takes its subject from the title; `docket check` recovers a closed item's pull request from the newest subject naming its id; so the numbers were unrecoverable. Three errors, `bin/docket check` exiting 1, `make check` failing on a clean checkout of `main`, and the v0.3.0 release blocked until the numbers were read off GitHub by hand.

## Recovery — `subprojects/docket/src/docket/vcs.py`

`_merges_naming` keeps the subject scan as its cheap first pass (one history read for the whole set), then falls back — only for ids that pass did not answer — to the commit on the base that wrote `status: done` into that item's own file, reading `(#N)` from its subject. The commit that closed the item **is** the closure, so this is strictly more evidence than the subject scan, not less.

The parent tree is compared, so a *later* edit to a closed item — a `pr` backfill, a corrected brief — cannot be mistaken for the closure and record a false number. A false provenance record is worse than a missing one.

**Verified against the incident**, not just against tests:

```

PL-P909: #220
PL-SS9Q: #220
```

## Prevention — `tools/pr_title_check.py`

Refuses a pull request whose title does not lead with the ids its branch closes. Wired into `quality.yml` on `pull_request` only, since a push to `main` has no title. It compares the closed sets at **both ends** rather than reading the diff, so a closure arriving through a merge of the base is not blamed on this branch.

**Verified against the incident** — run over `92a8e55^..92a8e55` with #220's real title:

```
pr-title: this branch closes PL-P909, PL-SS9Q, PL-YHF1, but the title does not
lead with PL-P909, PL-SS9Q, PL-YHF1.
  Rename the pull request to lead with the ids, comma-separated:
    PL-P909, PL-SS9Q, PL-YHF1: <what it does>
```

## Why both, and why not the third option

Recovery alone leaves the wrong subject on `main` for good and only repairs after the damage. The check alone leaks whenever a merger retypes the subject in the squash dialog, which GitHub allows and no check on a title can see.

Searching the **commit body** stays rejected: a body carries ids of items a pull request merely *mentions*, so it would record false attributions.

## Security note

The title reaches the script through the **environment**, never a `${{ }}` interpolation inside a `run:` line. A fork's pull request title is attacker-controlled text, and pasting it into a shell command is the standard Actions script-injection hole.
