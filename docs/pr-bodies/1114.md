Before: `docs/WORKING_NOTES.md` carried one sentence saying PySide6 6.11.2 segfaults on `QDataStream` over a temporary `QByteArray` and that the persistence work would meet it the first time it decoded a saved blob. It had no reproduction, no rule to follow and no mechanism.

After: a `Measured:` thread records six constructor forms, each run 25 times in its own process on PySide6 6.11.2 / Qt 6.11.2 / CPython 3.14.7, the versions `uv.lock` resolves. 6.11.2 is also the newest PySide6 on PyPI, so no upgrade escapes it.

- `QDataStream(QByteArray(blob), QIODevice.OpenModeFlag.ReadOnly)` segfaults on every run, inside `QBuffer::readData` (from `QIODevicePrivate::read`, from `QDataStream::readBlock`).
- `QBuffer(QByteArray(blob))`, opened and read through a stream, reads `0` and `''` on every run, and `stream.status()` still says `Ok`. That is a plausible wrong value with no error, the worse failure of the two, and the item as filed did not know about it.
- The one-argument read-only `QDataStream(QByteArray(blob))`, a named array passed to either constructor, and `QBuffer()` followed by `setData(...)` all read correctly on every run.

Why it happens, with sources:

- Qt's `QDataStream(QByteArray *, OpenMode)` wraps the caller's array in `new QBuffer(a)`.
- Qt documents `QBuffer(QByteArray *)` as "The caller is responsible for ensuring that byteArray remains valid until the QBuffer is destroyed".
- PySide6's `typesystem_core_common.xml` gives neither constructor a `reference-count`, the element it uses to keep a pointer argument alive elsewhere (on `QReadLocker(QReadWriteLock*)`, for example).
- The one-argument constructor copies the array through `setData`, which is why it is safe.

Not a PySide quirk, and not reported: PyQt6 6.11.0 / Qt 6.11.0 fails both forms 25 runs of 25 (its `QBuffer` form segfaults rather than reading zeros), and its sip declarations keep no reference to the array either. PySide's development branch declares both constructors as 6.11.2 does, and a web search found no tracker report. In C++ the same mistake does not compile, so this is Qt's documented lifetime rule lost on the way to Python.

The thread gives a rule rather than a workaround: never hand a `QByteArray` to `QBuffer`'s or `QDataStream`'s constructor, or to `QBuffer.setBuffer`. It records what avoiding them costs, which is nothing planned:

- JSON bytes in `QMimeData` round-trip for a drag payload.
- `QBuffer()` with no argument encodes an in-memory PNG safely.
- Simulation state is already barred from Qt by the import boundary.

The one case needing a stream, reading bytes Qt itself wrote, uses Qt's own one-argument read constructor. The thread ends with a runnable reproduction. PL-KJXS, filed on this branch, is the check that would enforce the rule.
