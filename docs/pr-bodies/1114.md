After: a `Measured:` thread records the six Qt entry points that keep a `QByteArray *`, what each did over a temporary array, and the forms that are safe. Each form ran 25 times in its own process on PySide6 6.11.2 / Qt 6.11.2 / CPython 3.14.7, the versions `uv.lock` resolves. 6.11.2 is also the newest PySide6 on PyPI, so no upgrade escapes it.

- The six are `QBuffer(QByteArray *)`, `QBuffer::setBuffer`, `QDataStream(QByteArray *, OpenMode)`, `QTextStream(QByteArray *, OpenMode)`, `QXmlStreamWriter(QByteArray *)` and `QCborStreamWriter(QByteArray *)`. PyQt6 6.11.0's sip declarations name seven `QByteArray *` parameters across QtCore, QtGui and QtWidgets: these six, and `QIODevice::readLineInto`, which keeps nothing.
- PySide6 keeps no reference at any of the six: `sys.getrefcount` on the array is unchanged by each call, while `QReadLocker(lock)`, which PySide does keep alive, raises its lock's count by one.
- Over a temporary, `QDataStream`, `QTextStream` and both writers segfaulted 25 runs of 25. `QBuffer(array)` and `setBuffer`, read through a stream, returned `0` and `''` with `status()` still `Ok`: a plausible wrong value with no error, the worse failure. `setBuffer` read with `readAll()` segfaulted instead.
- The outcome is undefined behaviour and varies by script: a second session on the same versions saw `QXmlStreamWriter` return normally 5 of 5 and `QCborStreamWriter` segfault 1 of 5.
- Correct 25 runs of 25: the one-argument `QDataStream(array)`, any of the six over a named array, `QBuffer()` with `setData`, and the writers and `QTextStream` over a no-argument `QBuffer`. A Python `bytes` argument to `QDataStream`, `QBuffer` or `QTextStream` is refused with `ValueError`.

Why it happens, with sources:

- All six end in a `QBuffer` holding the caller's pointer: the four stream constructors wrap it in `new QBuffer`, and `QBuffer`'s constructor and `setBuffer` store it.
- Qt documents `QBuffer(QByteArray *)` as "The caller is responsible for ensuring that byteArray remains valid until the QBuffer is destroyed".
- PySide6's `typesystem_core_common.xml` gives none of the six a `reference-count`, the element it uses to keep a pointer argument alive elsewhere (on `QReadLocker(QReadWriteLock*)`, for example).
- The one-argument `QDataStream(const QByteArray &)` copies the array through `setData`, which is why it is safe. Qt gives `QTextStream` the same copying overload, but PySide6 removes it, so every `QTextStream` over a `QByteArray` binds the pointer, one argument or two.

Not a PySide quirk, and reported: PyQt6 6.11.0 / Qt 6.11.0 fails the `QDataStream` and `QBuffer` forms 25 runs of 25, and its sip declarations keep no reference to the array at any of the six. PySide's development branch declares all six as 6.11.2 does. A tracker report exists, PYSIDE-232 "Crash with QDataStream and QByteArray", found by a second session's web search; nobody here has read it, because this environment's proxy refuses bugreports.qt.io. In C++ the same mistake does not compile, so this is Qt's documented lifetime rule lost on the way to Python.

The thread gives a rule rather than a workaround: never pass a `QByteArray` where Qt's C++ signature takes `QByteArray *`. A call does not show which overload it binds, and two read alike: the one-argument `QDataStream(array)` copies, while the one-argument `QTextStream(array)` binds the pointer. It records what avoiding the six costs, which is nothing planned:

- JSON bytes in `QMimeData` round-trip for a drag payload.
- `QBuffer()` with no argument encodes an in-memory PNG safely, and carries text, XML and CBOR written through `QTextStream` and the two writers.
- Simulation state is already barred from Qt by the import boundary.

The one case needing a stream, reading bytes Qt itself wrote, uses Qt's own one-argument read constructor. The thread ends with a runnable reproduction whose `refcount` form is the deterministic re-measure after a PySide6 upgrade. PL-KJXS, filed on this branch, is the check that would enforce the rule at all six entry points.
