Answers the policy question `PL-QSWS` raised, with the option the project owner
chose: a periodic scheduled run against the latest interpreter with
dependencies unpinned, **reporting rather than gating**.

The two declined options are recorded in the item — "nothing scheduled, fix on
breakage" lets the delta grow to whatever width a gap produces, and automated
dependency pull requests are the broad automation the evidence this project
cites says accumulates noise until it is routed around (`PL-ZBJ0`).

## The policy

`ROADMAP.md` gains **"Keeping the toolchain current"**, placed before the debt
gate as a standing rule rather than milestone scope. It states what notices,
what deliberately does not happen (no auto-bumps, no version-bump campaign —
the current pins are correct today), why it reports rather than gates, and the
condition for retiring it.

The instance is already in the repository, which is why this is worth a policy
at all: `pyproject.toml` records that pydantic 2.12.4 began passing
`prefer_fwd_module=` to `typing._eval_type`, a keyword CPython added between
3.14.0rc2 and 3.14.0 final, and parameter loading in the scientific core
stopped working. One dependency, one patch version, one interpreter build.

## The mechanism

`.github/workflows/drift.yml` — monthly, plus `workflow_dispatch`. Two jobs,
both asking questions `quality.yml` is right not to ask:

| Job | What it resolves | What a failure means |
| --- | --- | --- |
| `dependencies` | `uv sync --upgrade` — the newest release every bound in `pyproject.toml` already allows. No constraint edited. | A dependency broke us inside a range this project has already said it accepts. Actionable with no judgment call about widening a bound. |
| `interpreter` | Newest stable CPython, with `requires-python`'s upper bound relaxed **in the runner only**. | The next interpreter is not ready for this tree, or this tree is not ready for it. |

uv refuses an interpreter outside `requires-python` — correct for every other
job here, and exactly what this one has to see past. The relaxation is a
scripted edit that **fails loudly if `pyproject.toml`'s shape changes**, rather
than silently falling back to re-testing the pinned version.

A non-failing `uv pip list --outdated` step reports what exists *beyond* the
declared bounds. Crossing a major bound is a deliberate migration, not
something CI should attempt, so this surfaces that a Flet 1.0 or a pydantic 3
has become available and then stops. Without it nothing would ever mention that
the migration had become possible, which was the largest gap in the original
finding.

## Why it cannot gate

The versions it resolves are outside anyone's control, so gating would let an
unrelated upstream release block this project's own work. It runs on a schedule
and never on `pull_request`, so a red result never blocks anything in flight.

Both jobs carry the retirement condition in their comments: if this becomes
weather rather than news, the workflow is the thing to delete, per the test
added to `CLAUDE.md` earlier in this session.

## Two honest limits

**Not verified end to end.** A scheduled workflow cannot be exercised from a
pull request. The YAML is valid and the steps use the same actions at the same
pinned versions as `quality.yml`, but **treat the job as untested until it has
been run once by hand** — `workflow_dispatch` is on it for exactly that.

**The `verify:` command was written after the work**, which is the opposite of
what the `docket` skill requires. It was checked against `origin/main` in a
scratch checkout before being recorded — exit 1 without the work, exit 0 with
it — so it discriminates, but that is a weaker guarantee than having watched it
fail first. Recorded in the item rather than passed over.
