Closes `PL-Y5WR` (the 30-day scenario cap is enforced nowhere as an explicit halt). Gate 1 goes to 19 of 121 cleared.

## The problem

The 30-day cap was set on 2026-08-25 to size a concentration history that no longer exists, and was carried forward as though it described the model. It did not, and nothing enforced it: there was no ceiling on elapsed simulated time anywhere in `core/` or `app/`, so a run could reach day 45 of a 30-day cap and go on displaying two-decimal concentrations. The v0.4.0 playback multiplier made that reachable — at 300x a 30-day case is about 2.4 hours of wall clock.

## The number, and why it moved down rather than up

The item proposed the fat compartment's ~42 h time constant as the scale a cap should be "many multiples of". That inverts the relationship. Many multiples of the slowest mode is the regime `docs/MODEL.md` already declines to stand behind: § "Published wash-in validation test" says outright that this model has no metabolism, and rejects the Yasuda papers' own multi-day elimination curves as a comparison because over days the missing metabolism is no longer negligible and neither is the fat group's flow. The fat time constant is a **floor** on a useful cap, not a multiplier for one.

What binds it is the omitted metabolism. Sevoflurane is the binding agent — 2% to 5% of the absorbed dose, beginning within minutes rather than late — and what makes omitting it safe over a case is that the same source finds metabolism does not contribute to the termination of clinical drug effect. True while ventilation and perfusion dominate the trace; progressively false once the only thing still moving is the slow tail this model gives no sink to.

**24 hours** clears every anesthetic this simulator teaches by a wide margin, is about 0.6 of the fat time constant so the slow-compartment demonstration survives intact, and sits near the outer edge of the exposure range over which that omission has been measured at all. The citation is marked **tier 2** in both the code and `docs/MODEL.md`: 24 hours is a declared envelope argued against the omission, not a value computed from a metabolic rate, and saying so is what keeps a review from reading as the authority for a stored value.

## What reaching it does

Halts — and does not present as a failure, which is the half the item did not anticipate.

- **Integer step-count comparison**, derived once per step size, so the boundary falls at the same step on every machine and deterministic replay holds across it. The interval is closed like the four flow ranges: at the shipped 0.1 s step a run completes exactly 864 000 steps, lands on 86 400.0 s, and the 864 001st is refused before anything advances.
- **`SimulationDomainLimitError`** subclasses `SimulationExecutionError`, so a caller that knows only the base classes stops the run (the safe default), while one that catches it specifically knows nothing failed.
- **The interface reads that type.** Status reads "Stopped — supported run length reached" rather than "simulation error", not in the failure's WARNING colour; the notice names the limit and why it is where it is, instead of describing a rollback that did not happen; Start is disabled, because the controller would refuse it. `supported_limit_reason` is a snapshot field of its own, separate from `failure_reason`.

Describing a correct model as a broken one misleads a reader as surely as the reverse — it spends the one signal this interface has for a real fault.

## Out of scope, named so it is not mistaken for a reason to raise the number

Volatile sedation in intensive care runs for days and is precisely the regime this model is wrong in. Reaching it is a model extension — metabolism first — rather than a raise of this limit.
