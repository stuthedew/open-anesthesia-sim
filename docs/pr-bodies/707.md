## The answer

**`tests/benchmarks/`, and the standard-library rule is a property of `tools/`.**

The second half was already decided in the tree rather than open. `tests/unit/test_tools_portability.py` holds the rule by *directory*, and its docstring says why: "Two directories qualify, for one reason. `tools/` is invoked by `make check` and CI; `.claude/hooks/` is invoked by Claude Code ... Neither goes through the project virtualenv." The promise is about how a file is invoked, not about its being runnable. A harness importing PySide6 and the package itself can only ever run inside the virtualenv, so it is outside that set and needs no exemption from it — and `CLAUDE.md` needed no edit, its sentence being scoped to "new tools" already.

That left where it lives. `tests/benchmarks/` over a `bench/` tree because the test tree already carries everything this needs and a new top-level tree would re-declare all of it: `tests/conftest.py` selects the `offscreen` platform; `tools/workflow_paths_check.py` puts both files on the product side of the lane boundary from their imports, with no `docket.toml` edit; `tests/integration/test_qt_rendering.py` is the instance the setup copies; and pytest collects nothing whose name does not begin `test_`, so the harness stays out of `make check` while sitting beside the suite that keeps it alive. What a `bench/` tree would have bought — "this is not a test" stated by the path — the module docstring states in a sentence.

## What landed

```
uv run python tests/benchmarks/frame_cost.py
```

About three seconds, no new dependency. It drives a real `SimulationController` and a real `SimulationView` shown at a fixed size under the `offscreen` platform, and times each frame's three stages: `controller.advance`, `SimulationView.present(False)` and `QApplication.processEvents()`. Steps per frame are derived from `SIMULATION_STEP_S`, `SIMULATION_TICK_INTERVAL_S` and `RENDER_INTERVAL_S` rather than written in, so a cadence change moves the measurement with it, and the rate is validated through `app/playback.py`'s own ladder.

**The third stage is the part a harness gets wrong, and it is why the method is worth keeping.** `ChartPlot.draw` is `setData`, `setPos` and `setTicks` throughout, so `present` returns before anything is rasterized and the frame is complete only once the event loop dispatches the paint. Measured on this container at the defaults, medians over three runs:

| stage | median |
| --- | --- |
| `advance` (simulation) | 12.0 ms |
| `present` (assembly) | 15.3 ms |
| `processEvents` (paint) | 13.1 ms |
| interface (2 + 3) | 28.4 ms |
| frame | 40.4 ms of a 200 ms budget |

A two-stage harness would have reported the interface at 15.3 ms — 46% low, in the flattering direction. The control, a second `processEvents`, costs 0.08 ms, which is what rules out reading stage 3 as fixed event-loop overhead rather than this frame's rasterization. Under Flet the same third position was held by `page.update()` against a serializing connection; the stage the toolkit charges for is never the one the code makes obvious.

Two configurations are refused rather than measured, so the harness cannot report a plausible number for a measurement that did not happen: a rate the interface does not offer, and a run whose elapsed simulated time does not match the steps asked for — which is what a halted or capped controller leaves, since `advance` then returns immediately and would report the simulation as free.

`tests/benchmarks/test_frame_cost.py` is the decidable half: that the harness still runs and still reports the stages it names. It asserts nothing about a duration — a threshold would measure the runner rather than the code — and runs at 1x over a 30 s warm-up, so it costs the suite about a second.
