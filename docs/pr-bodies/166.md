Closes `PL-768D` (the `tools/` import guard reads the running interpreter's stdlib, not the floor's) by route 4, approved 2026-09-01.

**This PR adds a second CI job, so its own CI run is the first proof it works — watch for `floor` alongside `checks`.**

## The problem, and why the obvious fix was the wrong one

`PL-QDH7`'s import guard allows any name in `sys.stdlib_module_names`. That frozenset belongs to the interpreter running the test — the virtualenv at 3.14 — not to the 3.11 floor `subprojects/docket/pyproject.toml` declares. A module added between the two passes the guard and is missing where it matters (`annotationlib`, `compression`).

The captured fix was to subtract a hand-written set of post-floor names. That set would have to cover every module added between the floor and whatever interpreter runs the suite, *forever*, so each Python upgrade silently reopens the same fail-open hole — a guard that re-creates its own bug on every upgrade.

Triage found the same gap one level out, and it changed the answer: **nothing in CI ran either tree at the floor at all.** `checks` reaches `doc_check.py` through `uv run python`, and `bin/docket check` through whatever system python the runner image ships. So *both* portability suites — the parse test's `ast.parse(feature_version=...)` gate and the import test's frozenset — were approximating a run CI never performed.

## What this does instead

Perform the run. `quality.yml` gains a `floor` job: `actions/checkout`, `actions/setup-python@v7.0.0` pinned to 3.11, then `python3 tools/doc_check.py check` and `bin/docket check`. That settles syntax, imports and runtime behavior together, with no list to keep current as the standard library moves.

It lands green as a guard rather than as a fix: both commands were run at 3.11.15 in the development container — the same invocation the job makes — and exit 0.

`python-version:` is set explicitly rather than inherited. Left unset the action reads `.python-version`, which pins 3.14.7 — the one interpreter this job exists not to test. The action's `action.yml` at `v7.0.0` was read directly to confirm the input name and that `update-environment` defaults true; the tag itself came from `git ls-remote --tags`, not from memory.

## The new test

`test_the_ci_floor_job_pins_the_declared_floor` holds the job's pin to `requires-python`, so raising the floor cannot leave CI exercising an interpreter the project no longer supports — the same drift the existing formatter-target check catches, one layer out. It also asserts the workflow carries **exactly one** `python-version` pin, so the `checks` job's deliberate absence of one (it would set `UV_PYTHON` and override `.python-version`) cannot be lost silently.

Both failure modes were watched, not merely assumed:

```
AssertionError: assert '3.12' == '3.11'
AssertionError: expected exactly one python-version pin in the workflow, found ['3.14', '3.11']
```

The workflow YAML was also parsed to confirm `python-version` stays the *string* `"3.11"` — unquoted it would parse as a float.

## What was kept, and why

The three approximations stay. They run before a push rather than after one, they name the offending file and import where a CI traceback would not, and they reach a file or a lazily-imported branch the job's two commands never touch. Their docstrings now record the bound with the real check named, instead of recording an open gap.

`subprojects/docket/tests/test_portability.py` needed no edit: its hand-maintained `ALLOWED_IMPORTS` is backstopped by the same job running `bin/docket check` at the floor.
