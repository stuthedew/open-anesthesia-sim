## The decision

`milestone:` was carrying two meanings — "shipped in this release", which `docket release` stamps, and "scoped to this release", hand-written onto frozen gate entries. Settled by the project owner on 2026-09-01: **it means shipped-in.** Membership of a release still being assembled stays in the gate subsection of that milestone's `ROADMAP.md` section, which `bin/docket wave` already parses.

The field is not split in two, because nothing needed the second meaning: `bin/docket wave` reports the same `33 cleared, 5 open` of 38 with the stamps present and with them removed, so gate accounting never read the field at all.

## Why it was worth failing on

Not merely ambiguous — silently lossy. `release.unreleased` selects finished work with **no** `milestone`, so a hand-stamped item is invisible to the release that ships it and is left out of that release's generated notes, permanently once tagged.

```
bin/docket release 0.2.8 --dry-run   # 46 items before, 56 after
```

All ten of the missing ones were `v0.2.8` gate work — the notes for "the workflow works" would have omitted most of the workflow work.

## The enforcement

`docket check` refuses both shapes of the wrong meaning:

- `_check_item` — a `milestone:` on an item that is not `done`, which cannot have shipped.
- `_check_milestones` — a `milestone:` naming a version above the project's current one, which is a release that has not been cut.

The second needs a fact the store does not hold, so `analyze` takes `version` beside `history`, `landed` and `closures`, and `cmd_check` passes what `read_version` reads. Where either side is not `major.minor.patch` — a project versioning by date, a release named `v1.0-rc1` — the comparison is not made rather than guessed at, the same refusal `_check_provenance` makes on a shallow clone.

Run against the store as it stood, the rule named exactly the ten items the dry run had been omitting.
