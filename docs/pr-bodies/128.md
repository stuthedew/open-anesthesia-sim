Closes the third hole in how the queue reports what is open. An item is closed by hand, so work that merges without `status` being set leaves the item `ready` forever — it keeps its place in `next`, `wave` and `gate` count it open, and the next session re-derives what is already on `main` before finding out. Four instances are known (`PL-XCYB`, `PL-ZQ9C`, `PL-1TPM`, `PL-0RS6`) and every one was caught by a person.

## How it works

`verify.already_passing` runs each open item's own `verify:` command and returns a `LandedReport`; `checks._check_landed` turns that into a grooming advisory. The report is threaded into `analyze` as an optional input beside `history`, so `checks.py` stays pure and every command except `check` skips it — this is the only check that *executes* the project rather than reading it, and `next` and the digest are asked on every session start.

The brief's choice of `verify:` over commit subjects held up: of the thirteen open items whose id led a commit subject on `main`, eleven were capture or triage commits.

## It names candidates, never a verdict

A passing command is consistent with two findings no exit status can separate — the work landed, or the command does not discriminate and would have passed before the work too. Measured against the store, the second reading was eight of the nine named, so the wording leads with the possibility rather than the conclusion. Both readings close: by setting `status: done`, or by giving the item a command that fails until its work exists.

The decidable half is reported as such. A command recorded against more than one open item cannot prove any single one of them done, whatever it returns.

```
PL-2HTF, PL-3CBS, PL-4YY1, PL-KQKM, PL-M58K, PL-MS54, PL-TH7P, PL-WB0X, PL-XH1D
are open but their `verify:` command already passes (9 of 29 checked): either the
work landed and the item was never closed, or the command does not discriminate
and proves nothing. PL-2HTF, PL-4YY1, PL-KQKM, PL-MS54, PL-XH1D share a command
with another open item, which cannot prove any one of them done - give each its own
```

## Two conditions decline rather than answer

Same reason `merged_pull_requests` declines on a shallow clone — an empty result meaning "could not look" must never render as "looked, found nothing".

- **A nested run.** Two open items record `verify:` commands ending in `bin/docket check`. Unguarded, the outer run re-enters itself once per candidate and each re-entry does it again. Children get `DOCKET_SKIP_LANDED` and skip this one question while still validating the store.
- **Nothing could be executed.** Every command returning 127 is what a bare checkout with no virtualenv looks like from here, and is indistinguishable from a clean store unless reported as a refusal.

## Found on the way

The `docket` skill's own table recommended `python3 tools/doc_check.py check` for documentation items. It passes whenever the docs are internally consistent, which they are before the item is started too — that row is the source of five of the eight false candidates. The table now pairs it with a `grep` for the text the item adds, and the section says to watch a command *fail* rather than merely to run it.

Two findings captured rather than fixed here: `PL-L9JS` (eight open items whose `verify:` command passes without their work, so `docket verify` would ACCEPT a branch that did none of it) and `PL-MZH2` (`PL-D9H6`'s command is wrapped in literal quotes and exits 127 on every tree).

`PL-Y08X` rides along as a capture only: the session digest instructs every session to offer 0.2.8 on the line above the one saying its gate has 7 of 32 entries open.
