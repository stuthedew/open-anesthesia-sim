Four tags rather than three, because `Scope` already draws a distinction

`Required scope` sits in `later` under the anchor's own version, which is

| Tag | What it says |
| --- | --- |
| `[gate]` | on the anchor's frozen list, which is the current step |
| `[after the gate]` | in the anchor's own `Required scope`, which clearing its gate comes before |
| `[in scope]` | in the anchor's `Required scope`, its gate already clear |
| `[v0.5.1]` | a later milestone's section places it |
| unmarked | no section of the roadmap places the id |

**The legend is the load-bearing half.** Twenty-four feature rows print a
`next:` item and five are on the gate, so a tag on every row would bury the ones
that matter — but an untagged row is then indistinguishable from one nobody

rows, so `_plan_header` defines the blank once, naming only the tags the render
actually drew.

`placement_mark` and `PLACEMENT_MARKS` sit beside `placement_line` in `plan.py`
rather than in `render.py`: what the two must agree on is the *relation*, and
that is `scope.placement` in both.

## PL-KD98 — a finished milestone can now reach the release beat

`_shipping_the_gate` reached `RELEASE` on two arrangements, and a milestone
recording a gate **and** a `Required scope` of its own was neither — so `wave`
could never print `release` for that shape, whatever the state of its scope.
Both v0.4.0 and v0.5.0 are that shape. The beat stayed `implement` on a finished
milestone and the digest turned the non-answer into an assertion: `No release to
offer: the roadmap gives 0.4.0 to "the teachable case", which is unfinished`.

The brief preferred softening that wording, on the ground that a parser over
`Required scope` is the judgment half `CLAUDE.md` says not to script. Measured,
that parser already ships — `_subsection_ids` reads the subsection in full, and
`Scope.placement`, `MilestoneStates.ships_with` and `check_gate_dispositions`
all rest on it. And softening could not have worked alone: `_beat_line` and
`_release_advice` print one above the other, so an offer above a beat reading
`implement` is the contradiction `PL-D2GW` and `PL-Q2BJ` already cost. Fixing
the computation makes the existing wording true rather than hedged, which is
what the project owner approved.

- `MilestoneSection.own_scope_ids` carries the `Required scope` half alone,
  apart from the union `scope_ids` that answers placement — a gate can be clear
  with entries still open, and the union would read a milestone as unfinished on
  work deferred outside it.
- `ScopeStatus` / `scope_status()` split those ids into closed, open and
  unknown, as `GateStatus` already does. **Strictly**, with no blocker walk: a
  milestone ships when its scope is done rather than when the remainder is
  somebody else's fault, and an unknown id withholds completeness instead of
  being guessed either way.
- `_shipping_the_gate` becomes `_release_due`, answering *what* to release
  rather than *whether*. Gate 0's exception is tested first, and the order is
  load-bearing: a gated milestone whose scope happens to be complete must not be
  offered ahead of the release its own gate earned.
- The third arrangement does not consult `step`. `_current_step` puts the
  project on the row **after** the last milestone it released — here the
  `v0.4.x` patch track, carrying `(0, 4, -1)`, a track marker rather than a
  number anything can be cut at — so an arrangement reading `step.version`
  would have declined on the very project that filed the item. `release_version`
  and `release_name` on `Wave` exist for the same reason: left to read
  `plan.step`, `release_offer` fell back to the bump's arithmetic and offered
  `0.4.21` directly above a beat reading `release v0.5.0`.

```
Gate      recorded under "v0.5.0 - the case you can branch" (160 entries, 160 ids)
          160 cleared, 0 open
Scope     the Required scope of v0.5.0 — the case you can branch (21 ids)
          21 closed, 0 open
Beat      release v0.5.0 — the case you can branch - its gate is clear and all 21 Required scope ids have closed
```

The `Scope` block is withheld while the gate is open — there the gate block
already says what is due, and `format_wave`'s budget is five lines read beside
the digest. Once the gate clears, the scope is the only remaining question.

Measured against the live roadmap: v0.4.0's `Required scope` is **16 of 17 ids
closed**, the one open being `PL-B9PY` (decompose `SimulationView` so two runs
can be rendered at once) — the brief said "twelve of thirteen", counting entries
by eye. v0.5.0 is 10 of 21, v0.5.1 is 1 of 13, and no section names an id the
store does not hold. **Today's beat is unchanged**: Gate 1 is open, so it is
still `clear the gate` and the `Scope` block stays withheld.
