## What was wrong

`bin/docket next` printed "In scope for v0.4.0 — the teachable case, the step
the project is on" while `bin/docket wave`, in the same checkout, printed
"step 2 of 10: v0.3.0 — the foundation". The two commands a session reads at
its start contradicted each other about which release the project is on.

**The capture called this a label defect and said the ranking was right. It was
not**, and measuring before fixing found the worse half.

v0.4.0's section places **29 ids: 22 on the gate and 7 in `Required scope`
only** — `PL-011`, `PL-DHV7`, `PL-F52R`, `PL-R3KB`, `PL-SSBP`, `PL-VM40`,
`PL-ZRSP`. `Scope.current` was the section's whole `scope_ids`, so all seven
ranked as work the current step includes while the beat was `clear the gate`.
`ROADMAP.md` has the gate clear *before* the milestone it gates is implemented,
so none of them is current work. `next` was really offering one — `PL-F52R` sat
third, and `PL-DHV7` and `PL-VM40` are `P1`.

A session following `next` could therefore start v0.4.0 implementation
believing it was v0.3.0's, which is what `CLAUDE.md`'s "do not implement beyond
the current milestone" forbids and what the gate exists to prevent.

## Why it is one fix and not two

Labelling `PL-F52R` "on Gate 0's frozen list" would have been a *new* false
statement. The label cannot be corrected without first telling the gate's
entries apart from the milestone's own scope — and once that distinction is
computed, ranking on it is the same expression.

## The change

**Narrowing.** `milestone_scope` takes an optional `clearing_gate`. Given one,
`Scope.current` is the gate's entry ids alone and the anchor's other
`scope_ids` move into `later` under the anchor's own version, so they read as
work a milestone names that the step has not reached. `wave` passes the gate
only on the `CLEAR` beat, so a milestone's `Required scope` becomes current
work the moment its gate clears. Opt-in rather than inferred inside
`milestone_scope`, because that function is given no beat and a caller reading
a section directly means the section.

**Label.** `Scope` gained `step_label` (the timeline row, set only when it
differs from the anchor) and `clearing` (whether `current` is a gate's entries
or a milestone's whole section). Two fields, not one: they answer "which row?"
and "on a gate?", and the beat can move off the gate while the labels still
differ — the release arrangement a single field would have mislabelled.
`plan.py` writes three accurate messages where it wrote one claim that was
false in two of the three cases.
