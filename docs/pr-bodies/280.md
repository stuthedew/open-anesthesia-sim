## The objection the brief raised, checked rather than assumed

`PL-FX3N`'s brief held that this was not automatic, because `-n` "defeats `-x` and `pdb`, which is part of what `make test` is for". It does not hold, in two independent ways.

**The recipe takes no arguments.** `make test` is `uv run pytest` and nothing else — there is no `ARGS=` pass-through — so neither flag could ever be given to it. A session debugging already invokes `uv run pytest -x tests/unit/test_x.py` directly, which this does not touch. The target being protected for debugging cannot debug.

**`-n auto` specifically does not defeat the debugger anyway.** Given `--pdb`, xdist sets `numprocesses = 0` and distribution off and runs serially (`xdist/plugin.py`, `pytest_cmdline_main`, the `numprocesses in ("auto", "logical")` branch); it is a *pinned* width that raises `--pdb is incompatible with distributing tests`. Confirmed against pytest 9.1.1 / pytest-xdist 3.8.0: `-n 2 --pdb` is a usage error, `-n auto --pdb` drops into the debugger exactly as a serial run does. That is a second reason to prefer `auto` over a number, beyond the machine-portability argument `PL-WCZV` gave.

`-x` still stops the run under both, letting the in-flight workers finish their chunk first, so more tests run before it stops (probed at 400 tests: 8 serially against 139). Theoretical here, for the reason above.

**Not `make test-fast`**, the brief's other option: a second target leaves the default slow, which is the whole complaint, and gives the flag a fourth home.
