## The defect

`Scope.placement` called an id `in-scope` when the current milestone's section named it anywhere between that heading and the next one. Naming was the whole test, so a section that named an id *in order to say it is not an entry* marked it as one.

`bin/docket next` on `main` at `7ee92ea` ranked `PL-68XK` (check that a recorded commit hash resolves) **second**, above three genuine entries, with the reason:

> In scope for v0.2.8 — the workflow works, the step the project is on.

read out of the paragraph in that same section which says:

> PL-68XK … is a different case and is *not* admitted by this rule: it predates the freeze and was excluded from the approved list deliberately.

The more carefully this project records why an item is *not* an entry, the more ids the reader mis-placed.

## The rule now

A section places an id from two structures and nothing else, each read by its own grammar:

- **the frozen list**, by its entries' heads — an entry is one bullet per problem, and an id later in the sentence is prose about another item;
- **`Required scope`**, in full — a milestone names what it covers in whatever grammar the sentence wanted (`(queue item PL-DHV7)` mid-bullet, or a paragraph), and the heading has already said that everything under it is scope.

Everything else in a section — its goal, its definition of done, its commentary, its exclusions — is read as prose and places nothing.

**Reading the section's *lists* and skipping its prose was the obvious rule, and it does not work.** `PL-68XK` is also named mid-entry inside another bullet, so a list-wide read still counts it. That is why the frozen list is read by its entries' heads, and why the gate half of scope is taken from the already-parsed `GateEntry` objects rather than re-read — the ids a gate holds and the ids it places cannot then drift apart.

## What it costs, and why that direction

Scope recorded *only* in a section's prose is now placed nowhere. That is the safe failure: an unread mention makes no claim, where an over-read one told a session that work a milestone excludes was the work that milestone was waiting on. The same silence now covers a milestone's own `Explicitly out of scope` list, which is captured as `PL-6P9Y` rather than fixed here.

Three ids paid that cost immediately. v0.4.0's gate prose says `PL-VM40`, `PL-F52R` and `PL-ZRSP` "appear in Required scope above" — and their ids did not. Those three bullets now print them, in the convention four sibling bullets already use, so the section's structure says what its own sentence claims.
