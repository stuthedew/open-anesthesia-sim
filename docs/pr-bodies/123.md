## The hole

`branches_in_flight` returns a `FlightReport` naming both what is in flight and the refs whose history this checkout could not read to find out. `in_flight_ids` returned only the first half — a `set[str]` cannot carry the second — and that set was what `next`, `list`, `status`, `concurrent`, `delegable` and the session digest all read. Each of them presented a partial reading as a complete one: a session was told an item was startable when the truth was that one ref went unread and might be carrying it, and the collision surfaced at push time. Only `docket flight` printed the gap.

Not hypothetical. This container held exactly one such ref while the work was being done:

```
$ bin/docket flight
No branch carries an item id, in its name or at the front of a commit.

1 ref cannot be compared with origin/main on the history this checkout holds, so what it carries is unknown:
  origin/Review_articles

$ bin/docket next          # before
... 3 suggestions, and nothing about the ref
```

## The fix is the type, not a line of output

`in_flight_ids` is gone. `FlightReport` grew an `ids` property, and every caller takes the whole report and reads the ids off it, so the gap travels with the answer instead of being dropped at the boundary — a caller that wants to ignore it now has to do so in writing, which is what stops the next one re-opening the hole. `render.format_unread` owns the one sentence all six print:

```
1 ref could not be compared with origin/main on the history this checkout holds,
so work in flight on it is missing here; `bin/docket flight` names it.
```

It reports rather than refuses, for the reason the rest of that read does: a ref past a truncated clone's horizon is the ordinary state of an agent session's container, not an error in it.

## Found on the way

`_flight` resolved its root with `find_root()` while every other command resolves it from the store, so `docket next --items <some other queue>` answered about in-flight work in whatever repository the command happened to be run in — the wrong-project error `_load`'s own docstring guards against. Fixed, and that is also what made an end-to-end test possible.
