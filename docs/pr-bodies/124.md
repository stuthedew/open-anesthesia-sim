## The hole

`branches_in_flight` reads an item id two ways, and only one of them needs history. `^origin/main` can exclude the default branch's own work only where the checkout holds it; `claude/pl-k7qx-short-slug` names its item in a checkout holding nothing at all.

Both reads were discarded together. A ref that failed either of the two guards went to `unreadable` before the name loop ran, so the id the checkout was certain of was thrown out with the ids it could not prove — and `docket next` then offered an item a live session was holding, which is the collision the whole read exists to prevent. PL-MGNC added the second guard, so the exposure had grown rather than staying where PL-KWC1 left it.

## The fix

The name loop now runs over the candidates in either half. Such a ref is reported in `branches` for the id its name proves **and** in `unreadable` for the ids its commits might have added — one ref, both halves, which is what the report's two fields could always say and no caller had to change to receive.

**The direction is the opposite of PL-MGNC's guard, deliberately.** A guard refuses an id *inferred* from a walk the history cannot support, where being wrong withholds startable work under the digest line telling a session not to start it again. A branch name proves its id outright, and what stays open is only whether the branch has landed — the cheaper uncertainty, because an item whose work landed is closed and never offered anyway. A ref the default branch already contains never reaches this read at all, which is what bounds it, and `test_a_landed_branch_contributes_nothing_however_its_name_reads` holds that bound.

Two rendered sentences moved with it, because both had claimed too much once the name half survived: `flight` now says what a ref's *commits* carry is unknown, and the queue-wide line PL-S1P1 added now says any item its commits carry is missing. Saying work in flight on it was missing would have been the same false completeness in reverse.
