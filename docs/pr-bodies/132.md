Closes `PL-1Q3S` (a merged pull request leaves a stale tracking ref, so the stop hook demands a push that would recreate a dead branch), an open entry of the v0.2.8 gate.

*(`BRANCH` stands for the merged branch's name throughout. The rule as committed in `CLAUDE.md` writes it in angle brackets; this body cannot, because the first version of it had them stripped as HTML tags, leaving the command reading `git branch -dr origin/`.)*

## What the defect is

GitHub deletes the head branch when a pull request merges, but the local `origin/BRANCH` survives. `~/.claude/stop-hook-git-check.sh` picks its comparison point with `git rev-parse "origin/$current_branch"`, which tests whether the ref *resolves locally* — not whether the branch still exists on the remote. So after a merge it keeps comparing against the deleted branch's last-pushed tip, and everything `main` has gained since counts as unpushed. Observed once as "There are 23 unpushed commit(s)" on a branch identical to `origin/main` with a clean tree.

Obeying it is worse than ignoring it: the push recreates a dead branch identical to `main`, with no content and no pull request, which a concurrent session then has to reason about.

## What changed

One bullet in `CLAUDE.md`, immediately after the commit-and-push bullet it qualifies, giving the restart sequence and the reason. Plus the item's closure notes.

## Two design points worth review

**Why resident prose rather than a check.** `CLAUDE.md`'s routing test asks for a check or a hook first, and none is available here. The stale ref comes into existence *mid-session*, at the moment the merge lands: the session-start digest and the `PreToolUse` branch guard have both already run and neither fires again, and a container is a fresh clone, so no later session holds the ref at all. A project-side `Stop` hook is the only repo-side trigger at the right moment and is not a real one — its ordering against the user-level stop hook is unspecified, so it would race the read it exists to correct. This is the `+12` resident lines `doc_check` reports.

**The rule does not say what the item said.** The item's **Fix.** paragraph proposes `git fetch --prune origin`. That would trade this defect for a worse one: a tracking ref for a branch the remote no longer has can be the only surviving copy of an item captured on a branch nobody merged. `fetch_remote` in `subprojects/docket/src/docket/vcs.py` declines `--prune` for exactly that reason, in as many words, and `bin/docket stranded` exists to recover what such a ref holds. The rule therefore names `git branch -dr origin/BRANCH`, which removes the one ref whose branch just merged and leaves every other stale ref for `stranded` to read. Verified here against a probe ref: it deletes the named remote-tracking ref and nothing else.
