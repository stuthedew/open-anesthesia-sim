Closes PL-1PSX (the control-input timeline is unbounded and regrouped in full on every frame), a Required-scope entry of v0.5.0.

## What changed

`SimulationView._refresh_view` called `group_adjustments` over the whole recorded timeline on every frame. The grouping is a property of the run rather than of the frame, and the overwhelming majority of frames follow one in which nobody touched a control — so a run that had accumulated a long record paid for the whole of it five times a second, forever, for an answer identical to the previous frame's.

`AdjustmentGrouping` in `app/control_timeline.py` holds the last result and returns it while the record is unchanged. The new-case discard warning is routed through the same object, so the count of what is about to be lost and the list of it can no longer come from two readings of one record.

## The key is the record's identity, not its length

The item proposed caching against the timeline's length, "since the record is append-only". It is not purely append-only: `_record_control_change` **replaces** the newest entry when one control moves twice inside a single simulation step, because the run was integrated only under the value standing when the step ran. That leaves the record the same length and a different record.

Keyed on length, the cache would go on serving the superseded grouping — the panel beside the chart would state a setting the run was never computed under, and the mark on the chart would stand for it. That is a presentation-correctness failure rather than a missed optimisation. The record is an immutable tuple the controller replaces whole, so `is` decides the question exactly and in constant time.

Both regression tests were confirmed to fail against a length-keyed implementation and pass against this one.

## No ceiling on the record, decided and recorded

Two reasons, both in `docs/MODEL.md` § "The control-input timeline" under "Bounds are displayed, not silent":

- Dropping the oldest entries would retire the beginning of a case, which is the part a learner returns to — "where did I dial back?" is the question the record exists to answer.
- It would bound nothing. `RunDefinition._segments` grows one stretch **and one keyframe** per accepted change — measured one-for-one with the timeline over 300 changes — and is not bounded either, so capping the cheaper of the two structures would cost the display's completeness and buy no memory bound.

## The item's premise for urgency does not survive measurement

The brief attributed the risk to the playback multiplier: "a drag emits settings at the event rate while simulated time advances at the multiplied rate, so a run played at 60x records many more entries per gesture." That is false. A change is recorded only once per simulation step, and a step is a property of the tick rather than of simulated time, so a drag records at most one entry per tick however fast the slider reports.

Measured across every supported rate, 600 slider events at 60 Hz against a 10 Hz tick:

| Playback | Entries recorded |
| --- | --- |
| 1x | 100 |
| 5x | 100 |
| 20x | 100 |
| 60x | 100 |
| 300x | 100 |
| paused | 1 |

Ten entries per real second of continuous dragging, identical at every multiplier. The brief now says so.

## Cost, measured

Against a 200 ms `RENDER_INTERVAL_S`:

| Entries | `group_adjustments` per frame | Append per entry | Record size |
| --- | --- | --- | --- |
| 1,000 | 0.88 ms | 0.007 ms | 0.09 MB |
| 10,000 | 8.8 ms | 0.05 ms | 0.9 MB |
| 100,000 | 94.6 ms | 0.89 ms | 8.8 MB |

After this change the regroup is paid only when the record changes. Reaching 100,000 entries takes some three hours of unbroken dragging.

The O(n²) append is left alone deliberately and the numbers are recorded in the item: it is on the input path rather than the render loop, is paid once per entry rather than once per frame, and a list would give up the immutability a frozen snapshot rests on.
